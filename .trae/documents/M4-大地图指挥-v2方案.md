## Context（为什么改）

v1 方案把「世界寻路」当作**地图表现的一部分**处理：扩 `PathfindingSystem` 跑 20×20 地形网格、桥/渡口靠「场景锚点格」隐式表达。本轮用户驳回，要求世界寻路是**独立的逻辑路径层**，与地图怎么画无关；桥/渡口、城池、关隘都在这层里显式定义，并配一个可视化编辑它的「世界地图逻辑编辑器」。

同时暴露出一个真实的结构问题：**逻辑对象与表现对象在同一位置重叠**（同一个坐标既有逻辑城池节点，又有渲染旗子/实体）。这会导致 z-order、命中检测、拖拽互相抢占——以及数据层已经有对应病灶：`SceneArmyOrderFlow.syncArmies` 无条件用实体质心覆盖 `armyStates.position`，把正在世界行军的单位「拽回」实体位置。本稿的核心就是给出分层答案，并顺带修掉这个 bug 的根因。

已定项（不再讨论）：D1 场景内每帧刻 + 重入补算；D8 仅 PC 左键点选 + 指令环 + 右键快捷；D9 痕迹 T1 不进 M4（`trace.enabled:false` 预留）；D10 通行色运行时首算 + 缓存；D5 公式结算 + 配置化数值。

## 2. 独立路径层（D2 · 核心）

### 2.1 定位

```
表现层：worldMap 地形网格（怎么画、场景锚点、缩略图）   ← 只读、不参与寻路
─────────────────────────────────────────────────────
逻辑层：worldLogic 节点图（谁能从哪走到哪、代价多少）   ← 唯一寻路权威
```

- 逻辑层**不复用** `WORLD_MAP_TERRAINS`、不读 `ProjectWorldIndex.coverage`、不进 `entityStore`。
- 两者只在**坐标**上对齐：节点 `position` 用世界坐标（与实体 `transform.position` 同一标尺，已实证 `WorldMapPanel` 直接把玩家 position 当世界坐标），编辑器可吸附到格（`cell` 仅编辑用）。
- 无 `worldLogic` 配置时，M4 退回运动路径：`ArmyOrderSystem._defaultMarch` 直线推进（现状零回归）。

### 2.2 数据结构（`game.project.json.worldLogic`，新增顶层键）

```jsonc
"worldLogic": {
  "schemaVersion": 1,
  "nodes": [
    {
      "id": "node.s03_yingchuan",
      "kind": "city",                  // city | pass | bridge | ferry | junction | camp
      "name": "颍川",
      "position": { "x": 1920, "y": 720 },   // 世界坐标 = 逻辑唯一权威
      "cell": { "row": 2, "col": 3 },        // 可选：编辑器吸附格，运行时不读
      "ref": { "type": "cityState", "id": "city.s03_yingchuan" }, // 可选：绑运行态/表现
      "ownerFactionId": "han_government",    // 初始归属；运行态以 armyStates 为准
      "garrisonRef": "army.s03.garrison",    // 可选：驻军编制引用（library.armies）
      "taxRate": 0,                          // 仅 pass 用（§7）
      "tags": ["fortified"]
    },
    { "id": "node.s03_bridge", "kind": "bridge", "name": "颍水桥", "position": { "x": 1600, "y": 900 } }
  ],
  "edges": [
    {
      "id": "edge.yingchuan_changshe",
      "from": "node.s03_yingchuan",
      "to": "node.s04_changshe",
      "mode": "road",                 // road | bridge | ferry | mountainPath | waterway
      "cost": 1.0,                    // 权重：越大越慢（乘基础行军速度的倒数）
      "bidirectional": true,
      "conditions": {
        "factionIds": null,           // null=全通；数组=仅这些阵营可走
        "crossingNodeId": null,       // 过河/关隘：必须控制该节点才可通行
        "blockedUntilDay": null,      // 剧情封路（按游戏日）
        "seasonal": null              // 预留：枯水/汛期
      }
    }
  ],
  "combat": { /* §6 公式参数 */ },
  "tariff": { /* §7 关税参数 */ }
}
```

**权重与通行条件的语义**

| 字段 | 语义 | 谁消费 |
|---|---|---|
| `edge.cost` | 基础权重（1=正常；`ferry` 建议 2.5～3；`mountainPath` 2） | `WorldRoutePlanner` |
| `mode` | 表现/音效/速度修正档位（`ferry` 行军速度 ×0.6，`bridge` ×0.9） | 行军执行器 |
| `conditions.factionIds` | 阵营白名单（`null` 全通） | `WorldLogicGraph.isEdgePassable` |
| `conditions.crossingNodeId` | 桥/渡口/关隘的**控制权门**：该节点由「可通行阵营」控制才放行 | 同上 |
| `conditions.blockedUntilDay` | 剧情临时封路 | 同上 |
| `node.kind === 'pass'` | 关隘：被敌方控制时**所有经该节点的边**判为不可通行（除非 `factionIds` 显式放行） | 同上 |

**桥/渡口（D3 定案）**：不做地形枚举、不挂场景锚点。表达为两件事——
1. 一个 `kind:'bridge'|'ferry'` 的节点（可被占领 = 可被封锁）；
2. 一条 `mode:'bridge'|'ferry'` 且 `conditions.crossingNodeId` 指向该节点的边。
编辑器里点两下（落节点 + 连边）即可；拆桥 = 删边或改 `blockedUntilDay`。

### 2.3 与现有三方的关系

| 现存物 | v2 关系 | 改动量 |
|---|---|---|
| `WORLD_MAP_TERRAINS` / `WorldMapCell` | **纯表现**：只服务 `WorldMapEditor` 画底图与 `ProjectWorldIndex` 校验；运行时寻路不读 | **零改动** |
| `PathfindingSystem` | **零改动**（不扩 A*；世界寻路走图最短路） | **零改动** |
| `armyStates` | 新增 `route`（逻辑节点序列 + 世界坐标点串）；`position` 在行军中以逻辑推进为准；`kind` 沿用 `army/city/pass/camp` | 加字段，旧档容错 |
| `ProjectWorldIndex` | 仍用于「场景在世界的落点」与表现层，不服务寻路 | 零改动 |
| `CityWarSystem` | 4C 战果落点（`prepareDraft` 复用，见 §6.4） | 行为不变，仅调用 |

### 2.4 数据存放

- **首选：`game.project.json` 顶层 `worldLogic`**（与 `worldMap`/`armyOrders`/`downedDrop` 同级）。
  理由：`SanguoGameLoaderCoordinator` 已整份持有 `project`，运行时零新增加载路径；`CanonicalEditorSession` 已支持提交 project 的任意字段（`WorldMapEditor` 就是提交 `worldMap` 的同款链路）。
- 备选（节点数膨胀后）：`project/world-logic.json` + `worldLogic: {"$ref": "...", "id": "world.logic"}`（`battles` 已有 `$ref` 先例）。v1 不启用。
- Schema：`GAME_PROJECT_SCHEMA` 增 `worldLogic: { type: OBJECT }`（形状校验放独立 `WORLD_LOGIC_SCHEMA`，见 §5.2）。

## 3. 逻辑 / 表现分层（结构问题正面回答）

### 3.1 问题本质

v1 把「城池/关隘/旗子」混在一个可视对象里：既有逻辑身份又有渲染身份，于是 z-order、命中、拖拽都要靠"谁在上层"来仲裁；数据层同病——`syncArmies`（表现→数据）与 `_applyExecutorResult`（逻辑→数据）同时写 `armyStates.position`。

### 3.2 四层方案

| 层 | 内容 | 是否可交互 | 是否持久化 |
|---|---|---|---|
| **L0 逻辑数据层** | `worldLogic.nodes/edges` 纯记录（无 canvas 对象、无 entity、无 z-index、无像素） | 否（数据） | 是（project） |
| **L1 投影层** | `WorldLogicProjector`：世界坐标 ↔ 面板像素 ↔ 编辑格；**唯一换算点** | 否 | 否 |
| **L2 表现层** | `WorldMapPanel` 运行投影（旗/节点/边）；编辑器画布投影 | 按视图模式 | 否 |
| **L3 交互层** | 按「当前视图」只激活一套命中表 | 是 | 否 |

规则：
1. **单向投影**：`逻辑 → 绘制`。绘制层永不回写逻辑坐标；拖拽只在 L3 写 `worldLogic.nodes[].position`，下一次投影自然移动。
2. **ID 绑定，不靠位置绑定**：表现对象要挂逻辑节点就带 `logicNodeId`；城池 `ref.id`、旗子 `ref` 都指 id。移动节点不需要改渲染数据，反之亦然。
3. **z-order 退出仲裁**：逻辑层固定画在最底（边 < 节点），不参与旗子/实体的 y-sort；命中检测**按视图模式二选一**，不再靠"谁盖住谁"。
4. **坐标系分离**：逻辑用世界坐标（+ 可选 `cell` 吸附），表现用场景/格/面板像素，换算只发生在 L1。

### 3.3 编辑器视图切换

三态：**表现视图**（现状地图编辑）/ **逻辑视图**（网格压暗只读，节点与边可编辑）/ **叠加只读**（两层同画，仅表现层可点）。

- 表现视图：场景锚点可拖，逻辑覆盖层只画不响应。
- 逻辑视图：节点可拖、边可连、条件面板可编辑；地形网格不响应点击（避免"拖一个旗子意外移动了城池节点"）。
- 叠加只读：给策划做"这张图画得和逻辑对不对得上"的对齐检查。

### 3.4 对 `syncArmies` 覆盖 position 那个 bug 的影响

**根因**：两处同时写 `armyStates.position`，没有权威声明。

- `SceneArmyOrderFlow.syncArmies` 每帧把实体质心**无条件**写回（且 `samples===0` 时会写成 `{0,0}`）；
- `ArmyOrderSystem._applyExecutorResult` / `advanceMarch` 也在写。

**分层后的规则（写进 spec）**：

| 单位状态 | position 权威 | 说明 |
|---|---|---|
| 有 `order.state==='executing'` 且 `route` 有效 | **逻辑层**（执行器） | 实体是投影：允许跟随但不回写；`syncArmies` 跳过 position |
| 无指令 / 已 `completed` / IDLE | **表现层**（实体质心） | 玩家手动挪动的军团以实体为准 |
| 无实体（离场/大地图） | 逻辑层 | 现状已如此 |

**修复点**：
1. `syncArmies` 仅在「无 executing 指令」时才写 `state.position`；有指令时只更新 `roster`（存活/阵亡 id）。
2. `samples===0` 不再写 `{0,0}`（保持原值）。
3. 若实体在场景内且有行军指令：可选让实体朝 `state.position` 收敛（`_projectStateToEntities`），但 4A **默认不做**（`ArmyCommandSystem.startMarch` 已在驱动），避免出现第三处位置写入者。
4. 回归保护：`armyStates.position` 在行军途中不被拉回；切场景回来位置连续。

这条改动本身就消掉了「逻辑对象与表现对象抢同一份数据」的问题，和 §3.2 的分层是同一原则。

## 4. 世界地图逻辑编辑器

### 4.1 宿主

**挂在现有 `world-map-editor.html` Tab 内**（`WorldMapEditor` 增加视图切换），不新开页面：

- 理由：它编辑的是同一份 `game.project.json`、同一套世界坐标、同一个 `CanonicalEditorSession`；新开页面会重复加载 project 与场景仓库。
- 新增模块：`editor/WorldLogicEditor.js`（视图控制器，只管 DOM/画布/交互）+ `src/core/world/WorldLogicGraph.js`（**编辑器与运行时共用**的纯模型：加载/校验/最短路/可通行判定）。
- `world-map-editor.html` 仅可能加一行标题/切换按钮容器（若 `WorldMapEditor` 自己渲染工具栏则零改动）。

### 4.2 编辑操作

| 操作 | 交互 | 写回 |
|---|---|---|
| 落节点 | 逻辑视图下双击空白（或工具栏「加点」+ 点画布），弹类型选择 | `worldLogic.nodes[]` |
| 移动节点 | 拖拽节点（吸附 `cell` 或自由） | `nodes[].position`（+`cell`） |
| 连线 | 从节点 A 拖到 B，选择 `mode` | `edges[]` |
| 改权重 | 选中边 → 属性面板 `cost` 数字 | `edges[].cost` |
| 通行条件 | 选中边 → 阵营白名单 / `crossingNodeId` / `blockedUntilDay` | `edges[].conditions` |
| 桥/渡口 | 落 `bridge|ferry` 节点 → 连边并设 `crossingNodeId` | 节点 + 边 |
| 关隘 | 落 `pass` 节点 → 设 `ownerFactionId`/`garrisonRef`/`taxRate` | `nodes[]` |
| 删除 | 选中 → Del；删节点级联删相关边并提示 | 三处同删（边/索引） |
| 校验 | 工具栏「校验」：孤立节点、重复 id、断边、`crossingNodeId` 指向非桥渡 | 只读报告（不写） |

### 4.3 保存链

`WorldLogicEditor` 只改内存草稿 → 点「保存」走既有 `CanonicalEditorSession` 提交 `game.project.json` 的 `worldLogic` 字段（与 `WorldMapEditor` 提交 `worldMap` 完全同构），**不新增第二条写盘路径**。校验失败拒绝保存并高亮出错节点/边。

### 4.4 运行时读取

`SanguoGameLoaderCoordinator` / `SceneGameplaySystemAssembler` 从 `gameLoader.project.worldLogic` 构造 `WorldLogicGraph`（一次性、不可变），注入：
- `ArmyOrderSystem`（`routePlanner` + `resolveTargetPoint` 支持 `{nodeId}`）；
- `SceneArmyOrderFlow`（`encounterDetector` 按图判定）；
- `WorldMapPanel`（节点/边只读投影）。

## 5. 遭遇：逻辑判定 + 四选确认（D4）

### 5.1 触发与暂停

```
每战略刻，行军中单位沿 route 推进
  ├─ 逻辑判定：目标边/节点上存在敌对单位或敌对城池/关隘
  │    └─ 且未处于 encounterCooldownTicks 冷却
  ├─ 进入 PENDING（order 保持 executing，但本刻不推进执行器）
  ├─ 玩家可见（地图面板打开 或 玩家就在该场景）→ 弹四选确认
  └─ 不可见 → 走 worldTravel.autoPolicy（缺省「战斗」抽象结算，不弹窗）
```

- 确认框超时（`decisionTimeoutMs`，缺省 8s）= **撤退**（最保守，不会自动损兵换胜）。
- 一把只弹一个：同一刻多个单位遭遇时排队，其余单位本刻暂停（不叠加弹窗）。
- 幂等：`order.encounterResolvedAt` 复用 3B 字段，确认后写值，避免同一次遭遇重复弹。

### 5.2 四选后果表

| 选项 | 进入哪套结算 | 是否消耗战略刻 | 是否改路径 | 士气/位置代价 | 可用条件 |
|---|---|---|---|---|---|
| **埋伏** | 抽象公式结算，攻方获得 `combat.ambushBonus`（缺省 +25% 攻击力） | **消耗 1 刻**（原地蓄势） | 否 | 胜：无；败：按败方退 | 仅当检测到「我方先发现」（敌方 `order` 非攻击且未处于警戒）且地形允许（`edge.mode` ∈ road/mountainPath/bridge） |
| **绕道** | 不进战斗 | 不消耗（立即改令） | **是**：排除该边/节点重算；无替代路则按钮置灰「无路可绕」 | 无士气代价；路程变长 | 图算法找到替代路径 |
| **战斗** | 玩家在该场景 → 实体展开实时战；否则 → 抽象公式结算 | **消耗 1 刻** | 胜：沿原路继续；败：退回上一节点 | 败方按 `defeatLossRatio` 损兵 | 总是可用 |
| **撤退** | 不进战斗 | **消耗 1 刻** | 是：清 route，改令回上一节点（无上一节点则回最近己方节点） | 士气 `-retreat.moraleCost`（缺省 10）；位置回退；进入 `retreat.cooldownTicks`（缺省 4 刻）该边免遭遇 | 总是可用 |

- 「消耗战略刻」的定义：该单位**推进暂停 1 个 500ms 刻**（`decisionHoldTicks`，缺省 1），不是新资源经济，也不扣全局刻数。
- 撤退后冷却防「原地反复撞同一敌人」导致弹窗风暴。

### 5.3 与在场展开的关系

- 选「战斗」且玩家在该场景 → 复用 3B/3D 的实体展开与 `CombatSystem`；结束走 `CityWarSystem` 战果链（城池/关隘）或纯伤亡回写（野战）。
- 玩家不在场 → `EncounterResolver` 纯公式，结果写回 `armyStates`（损兵/士气/位置），并 fire `unit.encounterResolved`（沿用 3B 事件名，payload 增 `choice`）。

## 6. 公式结算（D5 + D6）

### 6.1 结构

```
攻方战力 = 兵力×兵种攻击 × (1+统率/heroScale) × 阵法攻击修正 × 士气系数 × 情境修正(埋伏/多军团堆叠)
守方战力 = 兵力×兵种防御 × (1+统率/heroScale) × 阵法防御修正 × 士气系数 × (1+城防) × 地势修正
比分 = 攻方/守方 × 随机(0.9~1.1)
```

### 6.2 权重来源（全部来自既有字段）

| 因子 | 数据来源（既有字段） | 缺省回退 |
|---|---|---|
| 兵力 | `armyStates.roster`（存活 `unitIds` 数量）；若 `deployment.roster` 有 `{unitTypeId: count}` 则用它算构成 | roster 缺失 → 按 1 个单位算，并在事件里标 `degraded:true` |
| 兵种攻击/防御 | `library.unitTypes[].stats.attack/defense` | 未配 → 10/10 |
| 兵种克制 | `library.unitTypes[].dealMultiplier[敌方兵种]`（按数量加权平均） | 1.0 |
| 主将统率 | `library.heroes[].stats.command`（`armyStates.commanderHeroId` 指过去）；`level`、`rankId` 作小幅加成（`rankId` 有 `modifiers` 才生效） | 主将缺失 → 50（中性） |
| 主将武力 | `heroes[].stats.might` — **当前数据未配**，公式先按 0；字段预留 | 0 |
| 阵法 | `library.formations[].modifiers.attack/defense`（`armyStates.formationId`） | 1.0 |
| 阵法互克 | `worldLogic.combat.strategyMatrix[strategy_atk][strategy_def]`（键取 `formations[].strategy`：wedge/line/circle…） | 1.0（矩阵缺项） |
| 士气 | `armyStates.morale` → `0.8 + 0.4×(morale/100)`；低于 `routMorale` 直接判溃败 | 80 → 1.12 |
| 城池防御 | `cityStates[].buildingLevel` × `combat.cityDefensePerLevel`；× `(1 - damageRatio)`；× `(1 - 平均 buildingDamage)`；`morale` 另计入士气系数 | 城防 0 |
| 关隘防御 | `armyStates[passId]` 的部署/驻军 + `combat.passDefensePerLevel` × 关隘等级（无等级 → 1 档） | 0.15 |
| 地势 | 守方 `edge.mode`（bridge/ferry 攻方 -15%；mountainPath 守方 +15%；`node.tags` 含 `fortified` 再 +10%） | 1.0 |
| 多军团堆叠 | 同一节点/边参战的己方单位数：`1 + stackBonus×(n-1)`，超过 `stackLimit` 后每多一个改乘 `stackPenalty` | 1 支 = 1.0 |
| 攻守身份 | 攻方：`combat.attackerModifier`；守方：城/隘内 `combat.defenderInFort`，野外 `combat.defenderField` | 1.0 |

**差异化覆盖示例**（同一支军队打不同目标结果不同）：颍川（`buildingLevel 2`、`damageRatio 0`）vs 广宗营地（`buildingLevel 1`、`damageRatio 0.45`）→ 城防差约 3 倍；同一城由张角（`command 88`）与无名校尉（`command 45`）率队 → 统率项差 ~15%；1 支 vs 3 支同攻 → 堆叠项 +`2×stackBonus` 但受补给惩罚。

### 6.3 结果与损失

| 输出 | 规则 |
|---|---|
| `winner` | 比分 ≥1 攻方胜；<1 守方胜 |
| `casualties` | 败方 `defeatLossRatio`（0.3）× 比分劣势修正；胜方 `victorLossRatio`（0.12） |
| `retreatTo` | 败方退至 route 上一节点；无则最近己方节点 |
| `spoils` | 攻方胜 → 城池资源 `spoilsRatio`（缺省 0.15）转胜方所属城；关隘胜 → 关税累计额 |
| `rout` | 士气 < `routMorale` 时直接溃败（损兵 ×1.5，士气归 `routMoraleFloor`） |

### 6.4 落点

- 野战：`EncounterResolver` 返回结果 → `SceneArmyOrderFlow` 写回 `armyStates` + fire `unit.encounterResolved`。
- 城池/关隘：结果先转成 `BattleResult` 形状，交给 **`CityWarSystem.prepareDraft`** 入库（资源转移、`warState.battles`、`storyState.battleStats`、幂等账本）；`applyBattleResult` 的 checkpoint/回滚能力免费复用。
- 关隘的 `resourceTransfer` 用「关隘 → 胜方最近城」的累计关税（见 §7），避免给关隘造第二个资源账本。

## 7. 关隘：缩小版城池（D7）

### 7.1 数据表达：**独立 kind，不复用 `city`**

- `worldLogic.nodes[].kind = 'pass'`（逻辑身份）。
- 运行态：`armyStates[id].kind = 'pass'`（3B 枚举已含 `pass`，零扩张）。
- **不写 `cityStates[]`**：`CITY_SCHEMA` 的内政字段（`resources`/`buildingLevel`/`buildingDamage`/`damagePausedUntilDay`）对关隘全是负担，且 `CityWarSystem._validateInput` 要求 `resourceTransfer` 与城资源存在，硬塞会污染城池账本。

关隘携带字段（存 `armyStates` + `worldLogic.node`）：

| 字段 | 落点 | 说明 |
|---|---|---|
| `taxRate` | `worldLogic.nodes[].taxRate` | 关税税率（0.02～0.05） |
| `ownerFactionId` | `armyStates[].factionId`（运行态权威） | 归属 |
| `garrison` | `armyStates[].deployment.roster` | 驻军（复用部署结构） |
| `toll` | `armyStates[].supply.toll` | 累计关税（日结清空） |
| `level` | `worldLogic.nodes[].tags` 或 `node.level` | 关隘规模（1 档起） |

**被敌方控制时**：`WorldLogicGraph.isEdgePassable` 对该节点所有相邻边返回 false（除非边的 `factionIds` 显式放行）→ 必须绕路或先打（对应 4B 的「关隘封锁」验收）。

### 7.2 关税结算：新增 `PassTariffSystem`（小、纯、可单测）

```
行军/押运单位进入 pass 节点
  → PassTariffSystem.collect({ pass, mover, cargoValue })
      ├─ 同阵营：免税
      ├─ 中立关隘 / 已付费通行：按 taxRate 计
      └─ 敌对：拒绝通行（在路线规划阶段已判不可达）
  → 记入 armyStates[passId].supply.toll（当日累计）
AdvanceDayPipeline 日结
  → toll → 关隘归属方最近城池 resources（单一写点，防双算）
```

- 为什么独立系统而不塞 `ConvoySystem`：押运与军团都会过关，塞进押运会让军团关税走不到；`PassTariffSystem` 由行军执行器的「进入节点」回调统一调用。
- 为什么不在 `CityWarSystem` 结算：关税是**经过即计**的持续收益，不是战果。

### 7.3 常规收益收敛

关隘**没有**税收/建造/招募/建筑损毁/生产工位——它只提供：驻军防御 + 关税 + 封路。`CityPanel` 不对关隘显示城池卡；关隘只出「关隘卡」（归属/驻军/税率/累计关税）——属 4C 薄接线。
