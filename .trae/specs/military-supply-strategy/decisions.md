**三种入场身份（共用一条命令链）**

| 维度 | **接管 takeover** | **支援 support** | **旁观 observe** |
|---|---|---|---|

| 指挥权 | **有，但仅将令**（姿态切换 / 集火 / 撤退）；**部署类（兵种/阵型/主将位置）已锁死，连接管身份也不能改**（P22） | **无**（只指挥自己亲卫的三档：跟随/进攻/撤退） | 无 |
| 退出 | **逃亡**（退最近己方军营、降士气/声望、本场不可再接管） | **不算逃亡**（撤离即可，每场限一次） | — |
| 伤亡入账 | 军团 roster | **亲卫独立入账**（`supportRoster`） | — |
| 玩家倒地 | 按主将死亡/复活流程 | **可负伤不判负** | — |

- **玩家自己就是主将时没有「支援」档**（支援只用于帮 NPC 主将/友军势力打）。
- **「主将一律下场」与三身份不矛盾**（P22）：下场的是**军团的主将实体**（位置由战前部署 `commanderSlot` 决定），不是"玩家本体必须接管指挥"；旁观/支援只是**不接管指挥权**，主将由 AI 按军阵与姿态自动作战，**光环因此常驻**（在场即生效，仅阵亡/离场失效，见 06 §3.7）。
- **预演层已判负结束 → 只能「收容残部」**（`army.recoverRemnants`），不许接管/支援。

**三态收口对照（P19）**

| 维度 | 主将阵亡 | 主将逃亡退出（主动） | 战斗至结束 |
|---|---|---|---|
| 胜负 | **不判负**，部队继续 | **不判负**，部队继续 | `evaluateOutcome` 结算（唯一出口） |
| 玩家主将 | **走现有死亡/复活流程**；复活后退回最近军营，**不能返回本场** | 退回**最近的己方军营**（无军营 → 最近己方城池） | 留在战场随战果 |
| NPC 主将 | **直接退出战场**（不触发玩家死亡/复活流程） | 同左（撤离） | 留在战场 |
| 部队 | 继续作战，**由预演接管** | 继续作战，**由预演接管**（已定 ②） | 按战果结算伤亡 |
| 军团士气 | `commanderKilled.moralePenalty` 默认 **10**（一次性，与战败/逃亡两条阶梯**互不折算**） | 按**连续逃亡阶梯**：-5 / -10 / -15…封顶 **-30**（§5.4；原固定 -20 退役） | 本态不扣；按实际结果走 §5.4 战败阶梯（-10/-20/-30…封顶 -60） |
| 声望 | 0（阵亡不是失格） | `reputationPenalty` 默认 **-6**（-3~-12，每次逃亡都扣，不随阶梯放大） | 0 |
| 本场能否再上场 | 不能（本场） | **不能接管**，但可「支援」（每场限一次） | 不受影响 |
| 再统领该军团 | 玩家主将复活后可选其他军团；该军暂由 NPC 代领 | 可以（战后），需洗刷（06 §12） | 不受影响 |
| 连续逃亡 | — | 用**阶梯而非乘数**：-5/-10/-15…封顶 -30；`fledWindowDays`(30) 内再逃才累计、超窗清零；洗刷只 -1；换主将清零计数（`fledRecord` 保留） | — |
| 连带减兵 / 丢辎重 | 照常结算战损，**不加额外减兵** | 减兵 **5%~12%**（默认 8%，80% 进散兵池）+ 丢辎重 **15%~30%**（默认 20%） | 战败时减兵 **8%~18%**（默认 12%，60% 进池）+ 丢辎重 **20%~40%**（默认 30%） |

- **战场边界硬约束（已定 ⑥）**：接管身份越过战场边界前必须弹「是否撤退？」确认；**未确认则位置钳制在战场范围内**（不能因误触地形/传送被判逃亡）；确认才执行 `leaveBattle{reason:'commanderFled'}` 并计逃亡。支援身份越过边界直接放行（无惩罚）。

- **本组四项已全部收口**（原 ①~③⑥ 的 A/B 并列作废）：①=A、②=预演接管、③=不可再接管可支援、⑥=A+边界确认。**P20 声望与洗刷方案已于第六次拍板定稿**（声望做到 R3、洗刷 hybrid，见 06 §11.8 / §12.3；仍为设计稿、未落实现）。
- **改动成本**：`unit.joinBattle` / `unit.leaveBattle` 两个 operation + 预演态状态折算 + `battleIntervene` 参数块 + 指挥权门控（§3.6）+ 边界确认；`BattleSystem` 的 `selectMode` 判定条件扩大（"战场内存在可操控实体"），`evaluateOutcome`/`freezeResult` 不动。零回归靠"不配 `battleIntervene` 且无远程接管时行为与现状一致"。

### P20 声望独立建模（定稿 R3；R4 不做）

**三参数不可互换**（用户 2026-11-09 口径）：

| 参数 | 主体 | 语义 | 落点 |
|---|---|---|---|
| 民心 | **城池**（唯一主体，只有城池有居民） | 己方城镇对玩家的**配合度**（生产/缴税/征兵/逃散） | `cityStates[cityId].morale`（模块 7） |
| 士气·军团层 | 军团 / 驻军 / 关卡 / 军营 | 士兵对该军团的**配合度**（逃散/溃败/执行） | `armyStates[armyId].morale`（模块 3） |
| 士气·小队层 | **随行小队**（层级二） | 随行小队自身的**配合度**（独立初值/恢复/下限行为） | `storyState.companionSquad.morale`（新增） |
| **声望** | **玩家个人** × 势力/城池 | 各城池（己方与敌对）**看待玩家的态度**（交易/招募/准入/任务） | **新增** `state.player.reputation` |

- **民心不挂军团/关卡/军营/小队**；军营/关卡驻军只有士气，无民心。
- **小队层细则**：初值=来源军团队士气（新兵 60）；亲卫阵亡 -2/人（单场上限 -10）、3 日未休整 -3/日、玩家亲自逃亡 -5、胜利 +5、驻扎 +2/日；恢复 3/日、`clamp [5,100]`、`<10` 自动转防守拒冲锋；**玩家自任主将时小队层=军团层（镜像不独立扣）**，只有跟随他人/独立支援才独立记账（06 §11.7）。

- **按势力分记 + 关键城池覆写**（`byFaction` 主账本 / `byCity` 覆写 / `global` 派生展示 / `byHero` 预留不实现）；唯一写入口 `reputation.adjust`。
- **对民心只作输入项**（±5% 档位加成），**对士气不直接作用**（避免与逃亡惩罚重复计）。
- **分级（定稿 R3；R4 不做）**：R1 数据 + 展示 → R2 接招募名额 / 任务条件 → **R3 城池层 + 剧情写值 + 城池内价格** → **R4（个体英雄声望）不做**。
- **R3 四个价格入口**（全部按态度系数乘算）：①**商店买卖价** ②**装备修理费** ③**锻造工钱**（只乘工钱，材料数量不乘）④**招募成本**（单价 ×系数，名额另按名额系数）。统一入口 `PricingService.quote(kind, basePrice, {cityId})`，**只在最终报价处乘一次**，各子系统不各自乘。
- **下限保护（不能乘到 0；不做防倒卖）**：系数 `clamp [0.90,1.30]`；买价/修理/锻造下限 `max(1 铜钱, 基础价 × 系数)`；玩家卖价上限 **`×3`**（`sellPriceCapRatio`，**是卖价上限、不是态度系数上限**——倒卖须实际运货途中可被抢，风险成本已足够，第七次拍板取消防倒卖）；敌视档**拒售**（不做 ×1.30 还能买）。
- 完整方案（数据模型 / 来源消耗表 / 五档态度阈值 / 与 storyState 关系 / 成本）见 [06 文档](06-battle-plan-intervene.md) §11，R3 范围见 §11.8。

**洗刷污点**（06 §12）：污点 = `army.fledRecord`（军团层，连续逃亡与洗刷判定）+ `commanderStigma`（主将个人层，声望记账凭据），**不判负、不删军团、不扣兵力、不锁剧情**。**定稿 C「混合」**：默认**自动**（同军团下一场胜利回补一次），**剧情主角白名单走 B（`army.redeem` 剧情命令）**；参数 `redemption { mode:'hybrid', moraleGain:8, reputationGain:3, fledWindowDays:30, autoOnVictory:true, storyHeroes:["hero.zhangjiao"] }`。白名单**按该军团当前主将 `commanderHeroId` 匹配**，换主将后按新主将重新判定。防刷：仅 `fledWindowDays`(30) 内可洗、每份污点只回补一次、不超过逃亡前值、连续逃亡计数只 -1。

### P21 战败 / 逃亡：两本独立账（06 §5.4 / §5.5）

**士气阶梯（线性递增 + 硬封顶，不用指数）**

| 连续次数 | 战败 | 逃亡 |
|---|---|---|
| 1 | **-10** | **-5** |
| 2 | **-20** | **-10** |
| 3 | **-30** | **-15** |
| 4 / 5 / 6 | -40 / -50 / **-60** | -20 / -25 / **-30** |
| 7+ | -60（封顶） | -30（封顶） |

- 公式：战败 `-min(60, 10×n)`、逃亡 `-min(30, 5×n)`；两链**互不折算**、各自计数。
- 同一战斗可同时产生"逃亡 + 战败"两笔（主将跑后部队仍输），是**两个事件各扣一次**；"逃亡后打赢"只记逃亡。
- 声望每次逃亡固定 -6，不随阶梯放大（避免同一事双重放大）。

**重置条件**

| 条件 | 战败链 | 逃亡链 |
|---|---|---|
| 打胜一场 | **清零** | 不清（给洗刷资格） |
| 30 天无同类事件 | `decayDays` 每次 -1 | 超 `fledWindowDays` **清零** |
| 换主将 | **不清**（军团战绩） | **清零计数**（`fledRecord` 保留） |
| 解散重组 | 清零（新 armyId） | 清零 |
| `army.redeem` | 不适用 | 计数 **-1** |

**减兵与丢辎重**（事件型，一次性）

| 事件 | 减兵（占结算时剩余兵力） | 进散兵池（P15 可召回） | 丢随军辎重 | 追回 |
|---|---|---|---|---|
| 战败 | **8%~18%**（默认 12%） | 60% | **20%~40%**（默认 30%） | `recoverWindowSec` 600s 内回收 50%，触发率 60% |
| 逃亡 | **5%~12%**（默认 8%） | 80% | **15%~30%**（默认 20%） | 同上 |

- **地板** `manpowerFloorRatio` 0.30（与 09 `desertion.floorRatio` 同值、独立参数）；触地板只丢辎重、不再减兵。
- **与 09 分界**：断粮逃散=每日连续、本表=事件一次性；同一天先战斗事件后日结，共享 30% 地板、不叠扣。
- **与 02 分界**：以"入库边界"切分——在途只走 02 表（0/30/50/100%），入库只走本表；同批物资不同时受两张表。
- **幂等**：`state.battleLedger[battleId]` 单键（`settleBattle` 在 `state.transaction` 内先查后写），展开/收回、断线重连、读档重放都不重扣；顺序固定"记事件→扣士气→减兵→丢辎重→写键"。
- **改动成本**：`BattleLedger`（约 150 行，纯数据结算）+ `BattleSystem.freezeResult` 内一次 `settleBattle` 调用 + `leaveBattle` 一次调用 + 士气阶梯查表；无新系统、无 UI 改动，零回归靠"不配 `battleLedger` 时不启用（等价现状：无额外减兵/无阶梯）"。

### P23 战前部署位置与入口（第六次拍板：两处入口）

**定稿：两处入口并存，不新造"独立部署界面"（而是复用指令环页签 + 战场内页签）。**

| # | 入口 | 时机 | 动作 | 落点 |
|---|---|---|---|---|
| ① | **大地图「军团 → 战前部署」** | 非战斗状态 | 设**默认部署**（兵种构成 / 阵法 / 主将位置） | `armyStates[armyId].deployment`（随军团存档） |
| ② | **战场内部署页（`PRE_BATTLE`）** | 战场已加载、**未接战** | 临时调整本场 + **「设为默认值」勾选项** | 不勾 → `battle.deploymentOverride`（本场临时，打完即弃）；勾 → 同时回写 ① |

| 理由 | 说明 |
|---|---|
| 自动战必须能部署 | 玩家不在场的战斗（预演/抽象结算）只能靠大地图设默认值，否则永远无法部署 |

| 不复活被砍的 UI | 两处都是"指令环页签 / 战场内页签"，不新造 v1 那种战前计划大界面（06 v4 已砍） |
| 数据归属清晰 | 默认值挂 `ArmyState`（层级一），本场临时值挂 `battle` 上下文，互不污染 |

- **与 `DEPLOYMENT_LOCKED` 的冲突检查：不冲突。** ②的窗口严格在接战之前，`battle.deploy.lock` 一触发即转 `DEPLOYED` 冻结，与"战中任何身份不可改部署"是同一条规则的两个阶段；锁点从"进入战场"精确到"**接战**"。
- **取舍**：若策划更想"进入战场即锁"，把 ② 降级为**只读确认页**即可（不改结构）；若后续出现"反复进出战场刷部署"，加"每场仅可调一次"限制即可（同样不改结构）。
- **入口影响**：①模块 4：点武装单位 → 指令环「布阵」升级为「战前部署」页签（兵种摘要 + 阵法（含场景标签/地形偏好）+ 主将位置），非战斗可存为默认；②模块 6：`unit.joinBattle` 后进入 `PRE_BATTLE`（可调 + 勾选设为默认）→ 接战转 `DEPLOYED`；`unit.joinBattle` 本身**不携带部署参数**（它只管身份判定与战场加载）。
- **防重复**：①走 `army.deploy.preview` / `army.deploy.commit`；②走 `army.deploy.temp { battleId, ..., setAsDefault? }`（内部复用 ① 的回写路径，不另写一套落库）；锁口 `battle.deploy.lock`。
- **改动成本**：`deployment` 一个纯数据块 + `army.deploy.{preview,commit,temp}` 三个 operation + `battle.deploy.lock` 一个信号 + `unit.battleOrder`；零回归靠"不配 `deployment` 时不显示部署页、参数全默认"。

### P3 阵法无克制

**定稿**：`formations[]` **不设 counters 字段**。每个阵法只有 `modifiers { attack, defense, speed, ... }` 加成表，强弱差异全部体现在数值里。玩家看到的是"这个阵加攻、那个阵加防"，不是"这个阵克那个阵"。

### P4 兵种体系（3 大类 + 2 升级线）

**定稿树**

```
近战（melee）
 ├─ 枪兵     spear          T1
 ├─ 刀盾兵   shield         T1
 └─ 重甲士兵 heavy          T2  ← 由 枪兵 或 刀盾兵 升级（继承来源克制方向）
骑兵（cavalry）
 ├─ 轻骑兵   light_cav      T1
 ├─ 重甲骑兵 heavy_cav      T2
 └─ 弓骑兵   horse_archer   T2  ← 由 轻骑兵 或 弓箭手 升级
远程（ranged）
 └─ 弓箭手   archer         T1
    （弓骑兵双归属：兵种属骑兵，攻击方式属远程）
载具（vehicle，不算兵种）
 └─ 楼船 / 投石车 / 井栏 / 八牛弩 —— 走 vehicles 注册表，不参与兵种克制，
    但有独立"攻城加成 ×2"（对城池/工事），且不可被兵种克制影响
```

**替代差异**：把载具并入兵种 → 载具的载人/载货/攻城语义与兵种属性混在一起，`VehicleLogisticsSystem` 与 `CombatSystem` 双写；不分升级线 → 兵种等级只能靠数值成长，玩家感受不到"兵种质变"。

## 3. P4b 兵种克制设计（v3 改口径：无大类三角，骑兵压制一切非骑兵）

### 3.1 设计原则（4 条）

1. **骑兵压制所有非骑兵**——这是唯一跨类规则。原「近战 → 骑兵 → 远程 → 近战」大类三角**整体作废**，不再作为任何倍率的推导依据。
2. **唯一例外 X1 = 枪兵反骑**（Q1 定稿方案 A）：骑兵对枪兵 0.8、枪兵对骑兵 1.3。除这一格之外，骑兵对一切非骑兵均 ≥1.0。
3. **兵种特例层保留**：兵种之间的精细差异（近战内部、骑兵内部，以及 1 条弓骑兵必要的跨类例外）用特例表表达，**不从大类三角推演**。
4. **克制与等级解耦**：等级给属性（每级 +8% 攻/防），克制给战术；攻方低 ≥2 级时克制打折。

### 3.2 骑兵压制（核心规则，逐兵种取值）

骑兵攻击**任何非骑兵**取压制倍率；目标为骑兵时 **1.0**（同类不互克）。

| 骑兵攻 ↓ / 目标 → | 枪兵 | 刀盾兵 | 重甲士兵 | 弓箭手 | 骑兵（任何） |
|---|---|---|---|---|---|
| 轻骑兵 `light_cav` | **0.8**（唯一例外 X1） | **1.3** | 1.1 | **1.4** | 1.0 |
| 重甲骑兵 `heavy_cav` | **0.8**（唯一例外 X1） | **1.4** | 1.2 | **1.4** | 1.0 |
| 弓骑兵 `horse_archer` | **0.8**（唯一例外 X1） | 1.1 | 1.05 | 1.0（特例 E1） | 1.0 |

反向（非骑兵打骑兵）——**双向独立配置，允许不对称**（如弓箭手被骑冲 1.4，自身反骑只有 0.7）：

| 攻 ↓ / 目标 → | 轻骑兵 | 重甲骑兵 | 弓骑兵 |
|---|---|---|---|
| 枪兵 | **1.3** | **1.3** | **1.3** |
| 刀盾兵 | 0.8 | 0.8 | 0.8 |
| 重甲士兵 | 0.9 | 0.9 | 0.9 |
| 弓箭手 | 0.7 | 0.7 | 0.7 |

> **唯一例外 X1（Q1 定稿 = 方案 A）**：枪兵仍反骑兵——骑 → 枪 **0.8**，枪 → 骑 **1.3**。这是「骑兵压制一切」的**唯一豁免**，也是枪兵的全部职能所在（拒马）。除此之外骑兵对任何非骑兵均为压制 ≥1.0。

**取值理由**：刀盾兵最怕骑冲（无长兵、阵型易散 → 1.3~1.4）；重甲士兵抗冲（重甲 + 密集 → 1.1~1.2）；弓箭手最脆（贴脸即溃 → 1.4）；弓骑兵是"半骑半弓"，压制幅度整体低一档（1.05~1.1），且对射不占优（E1）。

### 3.3 兵种特例层（类内特例 + 1 条必要跨类例外）

**优先级高于 §3.2**：同一格若命中特例，用特例值。

| # | 特例 | 倍率 | 意图 | 类别 |
|---|---|---|---|---|
| E1 | 弓骑兵 → 弓箭手 | **1.0**（不吃骑兵压制） | 骑射对射无优势，弓骑兵不克同行 | 跨类（必要：弓骑双归属） |
| E2 | 枪兵 → 刀盾兵 / 反向 | **1.15 / 0.85** | 长兵压制短兵 | 近战内部 |
| E3 | 重甲士兵 → 枪兵、刀盾兵 / 反向 | **1.2 / 0.85** | 重甲碾压轻装 | 近战内部 |
| E4 | 重甲骑兵 → 轻骑兵 / 反向 | **1.2 / 0.85** | 重骑撞轻骑 | 骑兵内部 |
| E5 | 轻骑兵 → 弓骑兵 / 反向 | **1.3 / 0.8** | 轻骑追击弓骑 | 骑兵内部 |
| E6 | 弓箭手 → 重甲士兵 | **0.9** | 重甲减箭伤 | 近战受击 |

> E2~E5 成对双向；E1/E6 单向成立（反向按 §3.2 基础值）。

### 3.4 完整矩阵（7×7，定稿）

> Q1 定稿 = 方案 A（枪兵仍反骑）；原「方案 B（枪兵不再反骑，6 格不同）」**作废**，不再保留。

| 攻 ↓ 守 → | 枪兵 | 刀盾兵 | 重甲士兵 | 轻骑兵 | 重甲骑兵 | 弓骑兵 | 弓箭手 |
|---|---|---|---|---|---|---|---|
| **枪兵** | 1.0 | **1.15** | 0.85 | **1.3** | **1.3** | **1.3** | 1.0 |
| **刀盾兵** | 0.85 | 1.0 | 0.85 | 0.8 | 0.8 | 0.8 | 1.0 |
| **重甲士兵** | **1.2** | **1.2** | 1.0 | 0.9 | 0.9 | 0.9 | 1.0 |
| **轻骑兵** | 0.8 | **1.3** | 1.1 | 1.0 | 0.85 | **1.3** | **1.4** |
| **重甲骑兵** | 0.8 | **1.4** | 1.2 | **1.2** | 1.0 | **1.25** | **1.4** |
| **弓骑兵** | 0.8 | 1.1 | 1.05 | 0.8 | 0.8 | 1.0 | 1.0 |
| **弓箭手** | 1.0 | 1.0 | 0.9 | 0.7 | 0.7 | 0.7 | 1.0 |

> 读法：行 = 攻方，列 = 守方。骑兵三行除「枪兵」列（0.8）外，对所有非骑兵均 ≥1.0 —— 这就是"骑兵压制一切"在数据上的唯一体现；其余非 1.0 格全部来自 §3.3 特例层。

### 3.5 等级修正

| 规则 | 数值 |
|---|---|
| 等级本身 | 每级 攻/防 **+8%**（乘算，走 `stats` 成长，不进克制管道） |
| 克制倍率 | 固定值（§3.2/§3.3 表），**不随等级变化** |
| 攻方比守方低 **≥2 级** | 克制倍率衰减：**×1.3 类 → ×1.15**；**×0.8 类 → ×0.85**（其他倍率按同比例向 1.0 收缩 50%） |
| 等级能否反转克制 | **不能**——被压制方永远打不成优势，保证兵种选择有策略价值 |

### 3.6 数据落点

```jsonc
// library.json.unitTypes[]
{
  "id": "unit.spear",
  "name": "枪兵",
  "class": "melee",              // melee | cavalry | ranged
  "tier": 1,
  "upgradeFrom": [],             // 重甲士兵: ["unit.spear","unit.shield"]
  "stats": { "attack": 10, "defense": 8, "speed": 42, "range": 12 },
  "dealMultiplier": {            // 攻方倍率：未列出即 1.0（逐兵种显式配，不靠大类推导）
    "unit.light_cav": 1.3,       // 反骑（Q1=方案 A 定稿，唯一例外 X1）
    "unit.heavy_cav": 1.3,
    "unit.horse_archer": 1.3,
    "unit.shield": 1.15,         // E2 特例
    "unit.heavy": 0.85           // E3 反向
  },
  "takeMultiplier": {            // 守方视角：被打时倍率的覆盖（可空）
  },
  "damageTakenFrom": {           // 特例：重甲受弓 0.9
    "_example_heavy": { "unit.archer": 0.9 }
  }
}
```

- **全部特例（E1~E6）都能用 `dealMultiplier` 逐兵种键值表达**，不需要任何 `if (class === 'cavalry')` 代码分支。
- 「骑兵压制」不是硬编码规则，而是**在三条骑兵数据里把倍率写进 `dealMultiplier`**——引擎侧只做乘算。
- `CombatModifierPipeline` 只读表做乘算，**不含任何兵种/大类分支**——这是 M0 骨架的设计约束。
- 编辑器：内容库「兵种」类别，`class`/`tier`/`dealMultiplier` 三个字段（`dealMultiplier` 走"19 格倍率表单"，7×7 里除自身与同类外共 42 格，只允许配非 1.0 的）。

**改动成本**：改任何克制倍率 = 改 `unitTypes[].dealMultiplier` **纯数据，零代码**；改"骑兵压制"这个口径本身（例如将来又引入大类关系）才需动 pipeline（新增一层规则），属结构性改动。
