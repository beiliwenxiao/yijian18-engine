## 3. 三种入场身份

### 3.1 身份总表

| 维度 | **接管**（takeover） | **支援**（support） | **旁观**（observe） |
|---|---|---|---|
| 语义 | 接管该**军团指挥权**，自己就是主将 | 只带**自己的亲卫小队**作为独立友军参战，**无指挥权** | 不下场、无实体介入 |
| 触发 | 远程：大地图「接管——亲自操作将领和他的亲卫」/ 剧情命令（S02 张角）；现场：玩家本体就在战场 | 大地图「支援」/ 玩家本体实际抵达**同场景或相邻通路** | 默认（未做任何选择） |
| 玩家本体 | 在战场（现场）或被换绑为该军主将（远程），本体原地待命（§7） | **必须在场**（限本人+亲卫，不可远程） | 原地 |
| 操控对象 | 军团**主将**（远程 possess / 现场即本体） | 玩家本体 + 亲卫小队 | 无 |
| **场上主将** | **玩家操控**（现场=本体；远程=possess 的主将） | **该军团主将由 AI 接管**（玩家只带亲卫，不接管军团指挥） | **主将由 AI 接管**（整支军团含主将全 AI） |
| 指挥权 | **有，但仅限将令**：姿态切换 / 集火目标 / 撤退（§3.6）；**部署类仍锁死** | **无**：不能改军团阵型/姿态、不下将令；只指挥自己的亲卫小队（跟随/进攻/撤退三档） | 无 |
| 阵地/阵型 | **不改**（部署已锁定；只能发将令） | **不改**（军团阵型由 AI 维持；支援队独立编队） | 不改 |
| 退出 | **逃亡**（退回最近己方军营、降士气/声望、不能再次接管；**战场即该军营时改退最近的另一座己方军营或城镇**，见 §5.6） | **不算逃亡**（撤离即可，无惩罚） | 无 |
| 次数 | 每场 1 次（退出后不可再接管） | **每场限 1 次**（离开即用完） | — |
| 伤亡入账 | 军团 roster | **亲卫伤亡独立入账**（`supportRoster`，不占军团编制） | — |
| 玩家倒地 | 按 §5（玩家主将走死亡/复活流程） | **可负伤、不判负**（倒地只把玩家交回大地图，战斗继续） | — |
| 预演已判负 | 不可入场 | 不可入场 | 只能「收容残部」（见 §4.3） |

> **玩家自己就是主将时没有「支援」档**——支援只用于"帮别人打"（NPC 主将的军团、友军势力）。
> **「主将一律下场」与三种身份不矛盾**：下场的是**军团的主将实体**（位置由战前部署控制，模块 5 §3.3/§6.3），不是"玩家本体必须接管指挥"。选「旁观 / 支援」只是**不接管指挥权**，主将由 AI 按军阵与姿态自动作战；光环因此常驻（§3.7）。

### 3.2 「接管」的两个来源

| 维度 | 现场接管（onsite） | 远程接管（remote） |
|---|---|---|
| 触发 | 玩家本体**已在该战场位置** | 大地图按钮 / 剧情命令（S02 = 张角） |
| 玩家本体 | 在战场 ARPG 直接打 | **原地待命**（不跟随、不参战，§7） |
| 操控对象 | 玩家本体（= 己方主将） | 该军团**主将**（`possess` 换绑）+ 亲卫 |
| 战斗形态 | 军团预演就地展开为真实战斗 | 同左（共用展开器） |
| 退出 | **算逃亡**（越过边界需确认，§5.3） | **算逃亡**（UI「撤离」/ `leaveBattle{commanderFled}`） |

### 3.3 `selectMode` 自动判定

```
战场启动 / 预演展开时：
  战场内存在"玩家可操控实体"（经验证的接管身份：本体在场景 / 已被 possess 的主将 / 支援队本体） → INTERVENE
  否则 → OBSERVE（纯预演/抽象结算）
不弹任何选择 UI；剧情需要强制观战时，触发器用既有 blocked 通道锁玩家。
```

- `modeLocked` 维持"一场战斗内模式固定"；**锁模式 ≠ 锁退出**（退出走 `unit.leaveBattle`）。
- 战场内可控实体中途消失（主将阵亡/逃亡、支援本体倒地）→ 不切回 OBSERVE，仅把控制权交回玩家。

### 3.4 与 `possess` 的职责切分

| 命令 | 语义 | 是否新增 |
|---|---|---|
| `army.possess { armyId, heroId? }` | **只换绑主控**，可在无战斗时使用 | 既有，语义收窄 |
| `unit.joinBattle { armyId, identity:'takeover'\|'support', mode:'onsite'\|'remote', entry:'ui'\|'story' }` | **进入战斗**：`takeover` 走 possess+INTERVENE+展开；`support` 不 possess、只把亲卫小队挂成独立友军 | 新增 |
| `unit.leaveBattle { reason:'commanderFled'\|'commanderKilled'\|'supportLeft'\|'leftScene'\|'battleEnded' }` | **离开战斗**，按 reason 分流 | 新增 |

- 一个命令一个职责：`joinBattle` 管"进"，`leaveBattle` 管"出"，`possess` 只换绑。
- **命名定稿（第七次拍板）**：身份值 `command` **改名为 `takeover`**；`identity:'command'` 保留为**兼容别名**（等价 `'takeover'`），原因——10 文档与旧触发器示例里已写 `command`，保留别名可避免连锁改稿；**命令名 `unit.joinBattle` / `unit.leaveBattle` 不改**——它们是"进入/离开战斗"的动作名，三种身份共用，本身不含身份语义（若改成 `takeoverBattle` 会让"支援"也叫接管，语义反而错）。
- **旧名保留为别名**：战斗中的 `army.possess` → `joinBattle{identity:'takeover', mode:'remote'}`；
  `army.possess.release` → `leaveBattle{reason:'commanderFled'}`。旧触发器与 10 文档零改动。

### 3.5 「支援」细则

1. **必须实际抵达**：同场景或相邻通路（地图上 1 格内），不能远程支援。
2. **独立友军小队**：亲卫队单独编队（`supportSquad`），阵营=友军，不受军团 `army.*` 命令；只接受玩家本体所在小队的即时三档（跟随/进攻/撤退）。
3. **不改军团阵型/姿态**：军团的 `formationId`、`stance`、阵型偏移一律由 AI 维持——**而且这些本来就已经锁死**（部署类战中不可改，连「接管」身份也不能改），支援自然无从修改。
4. **伤亡独立入账**：`supportRoster` 单独记录，战后按 P15 散兵池规则处理，不进军团 `roster`。
5. **玩家可负伤不判负**：玩家本体在支援中倒地 → 交回大地图，战斗继续，**不触发 `raidDefeat`**。
6. **每场限一次**：离开或倒地后本场不能再支援（防"反复回血/刷贡献"）。
7. **预演已判负**：不能支援；只能「收容残部」（§4.3）。

### 3.6 指挥权门控（部署只看时机 / 将令仅接管 / 支援仅亲卫 / 旁观全禁）

**先分"改什么"，再分"什么时候能改"**——v4.4 核心划分：**部署只看时机，将令才看身份**。替换原"指挥权 = 接管就能改一切"的粗口径，以及第七次拍板前"部署按是否本方军团看身份"的写法。

| 可执行操作 | 归类 | 受理判据（唯一） | 接管 | 支援 | 旁观 |
|---|---|---|---|---|---|
| 兵种构成 `roster`、军团阵型 `formationId`/`rows`、主将/副将位置 `deployment.*`、军阵策略 | **部署类** | **`battle.status === 'PRE_BATTLE'`**（或非战斗状态） | 能 | 能 | 能 |
| 同上（**接战之后**） | **部署类（已锁死）** | `battle.status === 'DEPLOYED'` → 拒绝 `DEPLOYMENT_LOCKED` | 不能 | 不能 | 不能 |
| `unit.order` 战略指令（进攻/防守/运输/移动/扎营） | 战略类（非战斗） | 战斗外 | 战斗外可下；本战斗内不能改（改走撤退将令） | 不能 | 不能 |
| `unit.battleOrder{kind:'stance'}` 姿态切换 | **将令** | `identity === 'takeover'` + `DEPLOYED` 后 | **能** | 不能（只指挥自己亲卫） | 不能 |
| `unit.battleOrder{kind:'focus'}` 集火目标 | **将令** | 同上 | **能** | 不能 | 不能 |
| `unit.battleOrder{kind:'retreat'}` 撤退（战术撤军，士气 -3） | **将令** | 同上 | **能** | 只能让自己的亲卫撤（不改军团） | 不能 |
| 亲卫小队三档（跟随/进攻/撤退） | 小队指令 | 全程 | 能（亲卫跟本体） | **能** | 不能（无实体） |

```
部署类：if (battle.status === 'PRE_BATTLE' 或 非战斗) 且 军团属己方势力 → 受理
        否则 → 拒绝 DEPLOYMENT_LOCKED
        —— 不看入场身份：接管 / 支援 / 旁观一视同仁
将令类：仅 identity === 'takeover' 受理；support/observe 下发 → 忽略 + 提示"无指挥权"
```

- **两条判据不要混（v4.4 第七次拍板定稿）**：
  - **① 时机判据（部署专属，唯一门控）**：`battle.status === 'PRE_BATTLE'` → 可调；`DEPLOYED` → `DEPLOYMENT_LOCKED`。
  - **② 数据归属判据（不是身份）**：只能调**己方势力**的军团（`army.factionId` 属玩家势力 / 玩家对其有统属权）；敌方或友军 NPC 军团的部署，任何身份都不可调。这是"改的不是你的东西"，判的是**军团归属**，不是**入场身份**。
  - 身份（接管 / 支援 / 旁观）**完全不参与部署判定**：部署 ② 发生在开战前，本质是"把自己的部队摆好"，还没进入"谁指挥"的阶段。
- **若策划要更严**：把 ② 额外收窄为"仅 `identity === 'takeover'`"即可（只加一条与门的条件），但**不建议**——会让选了支援/旁观的玩家无法为本方军团做战前整备。

- **部署锁定时点（v2.3 精确化）**：锁的不是"进入战场"，而是**"接战"**——战场加载后先进入 `PRE_BATTLE`（可调部署），第一个敌对单位进入交战 / 战斗计时开始 → 转 `DEPLOYED` 并冻结；解锁在战斗结束回 `ASSIGNED`。字段语义见模块 5 §6.1/§6.3、模块 3 §3.2。
- **为什么接管身份也不能在接战后改部署**：部署是"带什么兵、什么阵、主将站哪"，一场战斗只能有一种答案；若接战后还能改，玩家会反复切阵型刷最优解，部署失去意义。接管身份的"指挥权"因此收窄为**将令**。
- **将令不写 `ArmyState.order`**：只影响本次战斗，战斗结束即失效；避免污染跨场景的战略指令状态。

### 3.7 战前部署归属 + 主将 AI 接管 + 光环常驻

**（1）战前部署在哪里做（第六次拍板：两处入口）**

| 入口 | 时机 | 动作 | 落点 |
|---|---|---|---|
| **① 大地图「军团 → 战前部署」** | 非战斗状态 | 设**默认部署**（兵种 / 阵法 / 主将位置） | `armyStates[armyId].deployment`（随军团存档） |
| **② 战场内部署页（`PRE_BATTLE`）** | 战场已加载、**未接战** | 临时调整本场部署 + **「设为默认值」勾选** | 不勾 → `battle.deploymentOverride`（本场临时）；勾 → 同时回写 ① |

- **冲突检查（与 `DEPLOYMENT_LOCKED`）**：不冲突。②的窗口严格在**接战之前**，接战即转 `DEPLOYED` 锁死，与"战中任何身份不可改部署"是同一条规则的两个阶段。若策划更想"进入战场即锁"，把 ② 降级为只读确认页即可（不改结构）。
- **命令**：①`army.deploy.preview` / `army.deploy.commit`；②`army.deploy.temp { battleId, ..., setAsDefault }`；接战由 `battle.deploy.lock` 收口。
- **`unit.joinBattle` 仍不携带部署参数**：它只负责身份判定（takeover/support/observe）与战场加载；部署调整是加载后的独立一步，判定只看 `battle.status === 'PRE_BATTLE'` + 军团归属，不看身份（§3.6）。
- **完整理由与对模块 4/6 入口的影响**见 [模块 5](05-formation-terrain.md) §6.3。

**（2）主将一律下场 + 旁观/支援时 AI 接管**：

| 身份 | 场上主将 | 光环 `heroAura` |
|---|---|---|
| 接管 takeover | 玩家操控（现场=本体；远程=possess 的主将） | 生效 |
| 支援 support | **该军团主将由 AI 接管**（玩家只操控本体+亲卫，不接管军团指挥） | 生效（主将在场） |
| 旁观 observe | **主将由 AI 接管**（整支军团含主将全 AI） | 生效（主将在场） |

- **"主将一律下场"与"玩家选旁观/支援"不矛盾**：下场的是**军团的主将实体**（位置由战前部署 `deployment.commanderSlot` 控制，猛将 `front` / 智将 `mid`~`rear`），不是"玩家本体必须接管指挥"。选旁观/支援只是**不接管指挥权**，主将仍由 AI 按军阵与姿态自动作战。
- **光环因此常驻**：只要主将实体还在场上（未阵亡、未撤离/逃亡），`heroAura` 就计入 `CombatModifierPipeline`；**只有阵亡或离场**（含玩家主将逃亡、NPC 主将退场）时该军团 `aura` 归 1.0，军阵 `modifiers` 不受影响。原"离场光环立即失效"是"主将不下场"时代的默认假设，已被替换为「**在场即生效、离场才失效**」。
- **预演阶段**（PREVIEW）不展开实体，主将按数值参数参与抽象结算（光环同样计入）；实体只在 PREVIEW → LIVE 展开时生成，位置取 `deployment.commanderSlot`。

## 4. 预演态 ↔ 真实态切换

### 4.1 两个态

| 态 | 形态 | 开销 |
|---|---|---|
| **PREVIEW（预演）** | 按"时间 × 兵力 × 修正"推进的动作预演：只有队列/交手动画与伤亡数字，**不生成逐兵实体** | 极低 |
| **LIVE（真实）** | 实体 + AI + `CombatSystem` 逐次结算 | 正常 |

### 4.2 展开（PREVIEW → LIVE）携带的状态

| 状态 | 来源 | 折算规则 |
|---|---|---|
| 已推进进度 | `preview.elapsed / duration` | LIVE 从该进度接续，不从头重打 |
| 累计伤亡 | `preview.casualties` | 先扣 roster，再按减员后数量展开（不双扣） |
| 军团士气 | `preview.morale` | 写入 `BattleState.morale`，不重算 |
| 战果修正 | `CombatModifierPipeline` | 同一份乘算（克制/军阵/地势/光环），展开时**不重算** |
| **主将实体与位置** | `armyStates[].deployment.commanderSlot`（缺省取 hero `deploySlot`） | **主将一律下场**：按 `front/mid/rear` 生成主将实体（§3.7）；展开发生在接战后，部署已冻结，展开不改阵型/位置 |
| 已发事件 | `battle.*` | 不重放（幂等键 `battleId + seq`） |

### 4.3 收回（LIVE → PREVIEW）

- 现场接管玩家确认撤退 → 收回实体、roster 回写，PREVIEW 从**当前实时战果**继续推进。
- **不回滚已发生伤害**（`battleId` 唯一、`freezeResult` 幂等，不能存档大法重打）。
- 可多次展开/收回（幂等），PREVIEW 状态挂 `blackboard.battles[battleId]`。
- **逃亡后一律由预演接管（已定 ②）**：不保留实体、不展开实时战场；战报可播一次残部简化动画。
- **预演已判负结束**：不再允许接管/支援，只允许「收容残部」（`army.recoverRemnants`：把预演残存兵员拉回最近军营，按残部规则重编）。

## 5. 三态收口（阵亡 / 逃亡退出 / 战斗至结束）

**核心不变式：主将的生死与去留都不是胜负条件**；胜败只由 `evaluateOutcome` 在战斗终结时给出。

| 维度 | 主将阵亡 | 主将逃亡退出（主动） | 战斗至结束 |
|---|---|---|---|
| 触发 | 主将实体 HP = 0 | 接管身份下主动退出（UI「撤离」或越过边界确认） | 任一方溃败 / `preBattleRules` 直判 |
| 胜负判定 | **不判负**，战斗继续 | **不判负**，战斗继续 | `evaluateOutcome` 结算（唯一出口） |
| 玩家主将 | **走现有死亡/复活流程**；复活后退回最近军营，**不能返回本场** | 撤离战场，退回**最近的己方军营**；无军营 → 最近己方城池；**若战场即该军营，退最近的另一座己方军营或城镇**（§5.6） | 留在战场，随战果 |
| NPC 主将 | **直接退出战场**（不触发玩家死亡/复活流程） | 同左（撤离） | 留在战场 |
| 部队 | 继续作战；**由预演接管**（不在场时无实体） | 继续作战；**由预演接管**（已定 ②） | 按战果结算伤亡 |
| 主将光环 `heroAura` | **失效**（该军团 `aura` 归 1.0；军阵 `modifiers` 仍有效） | **失效**（同上） | 生效（主将在场，§3.7） |
| 军团士气 | `commanderKilled.moralePenalty` 默认 **10**（一次性，与战败/逃亡两条阶梯**互不折算**） | 按**连续逃亡阶梯**：第 1 次 **-5**、第 2 次 **-10**、第 3 次 **-15**…封顶 **-30**（§5.4；原固定 **-20** 退役） | 本态本身不扣；只按实际结果走 §5.4 的战败阶梯 |
| 声望 | 0（阵亡不是失格） | `commanderFled.reputationPenalty` 默认 **-6**（-3~-12，**每次**逃亡都扣一次，不随阶梯放大） | 0 |
| 能否再接管 | 不能（本场） | **不能（本场）**——但可「支援」（每场限一次） | 不受影响 |
| 再统领该军团 | 玩家主将复活后可选其他军团；该军暂由 NPC 代领 | 可以（战后），需洗刷（§12） | 不受影响 |
| 再次逃亡 | — | 用**阶梯而非乘数**（§5.4）：-5 / -10 / -15…封顶 -30；`fledWindowDays`(30) 内再逃才累计，30 天无逃亡清零；洗刷只把计数 **-1**（不归零）；换主将清零计数（`fledRecord` 历史保留） | — |
| 玩家控制权 | 交回玩家（死亡流程或大地图） | 交回玩家（大地图） | 正常收回 |

### 5.1 定性：逃亡不是战术撤离

- **战术撤军** = 军团级命令（`unit.order{order:'retreat'}`，模块 3），阵型后撤、**无主将失格**，士气损失轻。**次序已对齐**：逃亡首档定死 **-5**，故 `tacticalRetreatMorale` 由 **6 降到 3**；已在 [模块 3](03-army-squads.md) §4.2（撤退档注记）、§6（参数落点）落地（v2.3）。
- **逃亡** = 玩家操作的主将**弃军而走**：综合代价 = 连续逃亡士气阶梯（-5/-10/-15…）+ 声望 -6（每次）+ 减兵/丢辎重（§5.5）+ 本场不可再接管 + 洗刷成本。
- 数据分开：撤退走军团队列，逃亡走 `leaveBattle{reason:'commanderFled'}`，**两套参数、两本账，不互相折算**。

### 5.2 与"战斗终结"的关系

- 逃亡/阵亡只改变**主将在不在场**，不推进任务链、不写战果。
- 终结两出口仍是 `raidVictory`（`waveCleared`）与 `raidDefeat`（全军覆没 / `playerSpecialFaint`）；它们内部**可以顺手调用** `leaveBattle{reason:'battleEnded'}` 收尾，但 `leaveBattle` 本身不等于结算。
- 支援中玩家倒地**不触发** `playerSpecialFaint`（不判负）。

### 5.3 战场边界确认（已定 ⑥）

```
接管身份下，玩家位置越过战场边界（地图格/地形切换/传送点）时：
  ① 弹出确认「是否撤退？撤退将按主将逃亡结算」
  ② 确认 → 执行 unit.leaveBattle{reason:'commanderFled'}（逃亡：士气/声望、回最近军营〔战场即该营则退最近的他营/城镇，§5.6〕、不能返场）
  ③ 取消 → 位置钳制回战场边界内（不让离开），本次不记逃亡
支援身份下越过边界：直接放行，无确认、无惩罚（支援撤离）
旁观无实体，不涉及
```

- 硬约束：**未确认不得离开战场范围**——防止误触地形/传送被判逃跑。
- 边界定义复用战场配置（`battlefield.bounds`，模块 4 通路/战场范围）；未配边界时按场景不超过战场触发区外扩 `boundaryPadding`（默认 64px）。

### 5.4 败绩与逃亡：两本独立账（2026-11-09 补充）

**核心**：战败、逃亡、主将阵亡是**三个独立事件**，各记各账、各扣各的，**不互相折算**。同一场战斗可能既记逃亡又记战败（主将逃走、部队最终仍败），但那是**两个事件各扣一次**，不是一件事扣两次；反过来"逃亡后部队打赢"只记逃亡、不记战败。

**记账字段**（`state.armyStates[armyId]`，随军团快照入档）：

```jsonc
"streak": {
  "defeat": 2,               // 连续战败次数（打胜清零）
  "defeatLastAt": 1720000000,
  "fled": 1,                 // 连续逃亡次数（换主将清零、洗刷 -1）
  "fledLastAt": 1720000000
},
"fledRecord": [ /* §12.2 污点历史，供洗刷判定 */ ],
"morale": 62                 // 军团层士气（唯一扣减目标）
```

**士气阶梯（线性递增 + 硬封顶，不用指数）**：

| 连续次数 | 战败扣士气 | 逃亡扣士气 |
|---|---|---|
| 1 | **-10** | **-5** |
| 2 | **-20** | **-10** |
| 3 | **-30** | **-15** |
| 4 | -40 | -20 |
| 5 | -50 | -25 |
| 6 | **-60（封顶）** | **-30（封顶）** |
| 7 及以上 | -60 | -30 |

- 公式：战败 `-min(moraleCap, moraleStep × n)`（默认 `min(60, 10×n)`）；逃亡 `-min(30, 5×n)`。选线性而非指数：连续败 4 次以上已接近崩盘，指数会让"翻盘"不可玩；硬封顶保证下限可预期。
- **为什么逃亡首档（-5）低于战败（-10）**：逃亡是"人跑掉、建制还在"，战败是"整场打输、伤亡入账"，后者对军心打击更大；但逃亡另有**声望 -6（每次固定，不随阶梯放大）+ 减兵/丢辎重（§5.5）+ 本场不可再接管 + 洗刷成本**，综合代价仍高于战败。
- **不与声望联动放大**：声望每次都只 -6，不按阶梯递增（否则同一事双重放大）；洗刷回补固定 `moraleGain:8 / reputationGain:3` 一次。

**重置条件**：

| 条件 | 战败链 | 逃亡链 |
|---|---|---|
| **打胜一场** | **清零**（`resetOnVictory:true`） | 不直接清零（只给洗刷资格，见 §12） |
| **经过 N 天无同类事件** | `decayDays`(30) 每 30 天 **-1**（0 = 关闭） | `fledWindowDays`(30) 超出窗口 **清零** |
| **换主将** | **不清**（战败是军团战绩，不是主将个人失格） | **清零计数**（逃亡是主将失格；`fledRecord` 历史保留） |
| **解散重组** | **清零**（新 `armyId` 天然新账） | 同左 |
| **洗刷 `army.redeem`** | 不适用 | 计数 **-1**（不归零，§12.4） |

**触发点与幂等（读档不重复结算）**：

| 事件 | 唯一提交出口 | 记账键 |
|---|---|---|
| **战败** | `evaluateOutcome` → `freezeResult`（唯一胜负出口） | `state.battleLedger[battleId] = { outcome, moraleApplied, troopsApplied, supplyApplied, at }` |
| **逃亡** | `unit.leaveBattle{reason:'commanderFled'}`（含边界确认后、断线超时） | `state.battleLedger[battleId].fled = { at, applied:true }` |
| **预演结算** | 与战败同一条（预演也走 `evaluateOutcome`） | 同上 |

- 统一入口 `settleBattle(battleId, patch)`：在 `state.transaction` 内**先查 `battleLedger[battleId]`**，对应账已 `applied` 则直接返回——展开/收回多次、断线重连、读档重放全部走同一键，天然幂等。
- 顺序固定：**先记事件（战败/逃亡）→ 扣士气 → 减兵 → 丢辎重 → 写 battleLedger**；中途异常重入时按 `applied` 标记断点续跑，不整段重扣。
- 逃亡后部队由预演打完（已定 ②），预演若判负会**再记一次战败账**——这是两个事件，允许；但同一 `battleId` 的逃亡账只记一次。
- **逃亡目标点不影响记账**：无论退往哪座军营/城镇、是否成功抵达、是否走"原地待命"兜底，士气阶梯、声望 -6、本场不可再接管都**照记一次**，目标点本身不产生额外扣减或减免（`battleLedger` 幂等）。目标点选取见 §5.6。

### 5.5 随机减兵与丢辎重（事件型，一次性）

| 事件 | 随机减兵（占**结算时剩余兵力**） | 散兵池（P15 可召回） | 随军辎重损失 | 追回机制 |
|---|---|---|---|---|
| **战败** | **8%~18%**（默认 **12%**） | 其中 **60%** 进 `scatteredPool`，30 日内 `army.regroup` 招回 | **20%~40%**（默认 **30%**） | 原地留 `supplyCache`：`recoverWindowSec`(600s) 内抵达可回收 `recoverRatio`(50%)，`recoverChance`(60%) 触发 |
| **逃亡** | **5%~12%**（默认 **8%**） | **80%** 进池（逃亡是脱队不是战死，召回率更高） | **15%~30%**（默认 **20%**） | 同上 |

- **逃亡目标点不影响减兵/丢辎重**：减兵比例与辎重损失只取决于"逃亡"这个事件本身，与退往何处无关；目标点不可达或走"原地待命"兜底（§5.6）也**不追加第二次**减兵。
- **兵力地板** `manpowerFloorRatio` 0.30（与 09 `desertion.floorRatio` 同值、**独立参数**）：单次事件后剩余兵力不低于**初始编制** 30%；已在地板时**只丢辎重、不再减兵**（保住"建制不散"这条既有护栏）。
- **与模块 9 断粮逃散的分界**：断粮是**每日连续**（`desertion.startDay/baseRate/maxRate`），此处是**事件型一次性**；同一天固定**先结算战斗事件、再跑日结**，断粮逃散按**扣减后**兵力计算，两者**共享同一 30% 地板**，后结算者触地板即停——不叠扣。
- **与模块 2 押运损失表的分界**：以"**入库边界**"为唯一分界——货物仍在车上/载具上 → 只按 02 表（胜 0% / 逃 30% / 败 50% / 载具毁 100%）；已入军团 `army.supply` → 只按本表。**同一批物资不会同时受两张表**（押运途中战败只结 02，入库后战败只结本表）。
- **丢失物资去向**：`supplyCache` 未被回收 → 50% 折算为敌方/劫掠者补给（与 02 §`recoverableRatio` 同思路），不留无限刷取点；超窗即清。
- **随机可复现**：种子取 `battleId` 哈希（`seededRand(battleId, 'troopLoss')`），读档重放结果一致；只影响减兵/丢辎重比例，不影响士气阶梯（阶梯是确定值）。
- **事件**：`army.defeated { armyId, battleId, morale, lostTroops, lostSupply }` / `army.commanderFled { ...同形状 }`，供战报、旁白、任务计数消费。

### 5.6 逃亡撤退目标点选取（2026-11-11 补边界）

| 项 | 规则 |
|---|---|
| 首选目标 | 距**逃亡发生位置**最近的**己方军营** |
| 战场即军营 | **若战斗地点就在该军营**（战场范围与该军营重叠，即"营即战场"）→ **排除该军营**，改选最近的**另一座己方军营或己方城镇** |
| 距离度量 | 大地图**通路格距离**（模块 4 通路网络），不是直线距离；目标无通路可达时按**不可达**处理，不按直线距离硬算；同距时按 `armyId` / `cityId` 字典序取小（确定性，便于读档重放） |
| 己方归属判定 | 目标必须是**玩家势力**所属（`armyStates` / `cityStates` 的归属方 = 玩家 factionId），且**未被围城、未被占领**；盟军营地不计（本规则只认己方） |
| 无可用目标兜底 | ① 退往**最近的己方主城**；② 主城也不可用 → **原地待命**：留在战场边界外侧（`boundaryPadding` 外），不再参与战斗、不重复记逃亡，UI 提示「无路可退」 |
| 不追加惩罚 | 目标不可达、兜底待命都**不追加**士气/声望/减兵扣减——§5.4 / §5.5 各只记一次（`battleLedger` 幂等） |

**地形差异**：

- **野外**：按上表正常执行；营地/寨子只要有己方军团驻扎即可作目标。
- **攻城**：战场即目标城池时，**该城不能作逃亡目标**（等同"营即战场"），改退最近的他城/军营；若该城是己方唯一据点 → 走"原地待命"兜底。
- **关隘**：关隘有己方驻军时按军营同规则；若战场覆盖关隘两端通路，逃亡目标须落在**通路另一侧**（`pass.passable === false` 时按不可达处理），避免"退出后仍处在敌军封锁线内"。

## 11. 声望系统方案（独立建模 · 设计稿，不落实现）

### 11.1 三参数必须分开（用户口径）

| 参数 | 主体 | 语义 | 现有/拟落点 |
|---|---|---|---|
| **民心** | 单个**城池/乡镇** | 己方城镇对玩家的**配合度**（生产、缴税、征兵意愿、逃散） | 城池 `morale`（模块 7 §3.3），声望只作其中一个输入项 |
| **士气** | 单支**军团** | 士兵对该军团的**配合度**（逃散、溃败、命令执行） | `ArmyState.morale`（模块 3） |
| **声望** | **玩家个人** × 每个**势力/城池** | 各城池（己方与敌对）**看待玩家的态度**（交易、招募、准入、任务开放） | **新增** `ReputationState`（本节） |

> 三者不是同一参数，不可互换：民心高 ≠ 声望高（富庶自守之城可能民心高但对你冷淡）；士气高 ≠ 声望高（能打不代表被天下认可）。

### 11.2 数据模型

```jsonc
// state.player.reputation（入档，走 state.transaction；跨场景持久）
{
  "byFaction": {                        // 主账本（默认按势力记）
    "yellow_turban": 35,
    "han": -42
  },
  "byCity": {                           // 覆写账本（关键城池可单独偏离势力）
    "S12": { "value": 20, "factionId": "han", "lastChangedAt": 12345 }
  },
  "byHero": {},                         // 预留（个体，不实现）
  "global": -8                          // 派生：主角所属势力权重和，仅展示
}
```

- **默认按势力分记**（数据量小、语义清楚：汉室/黄巾/地方），**关键城池可覆写**（`byCity` 优先于 `byFaction`）。
- 取值域 `[-100, 100]`；态度档由数值区间派生（§11.4），不另存。
- 全局声望 `global` 为**派生值**（不由玩家直接改），避免三处写冲突。
- 改动入口唯一：`reputation.adjust { factionId?, cityId?, delta, reason }`（reason 入日志，便于调试与战报）。

### 11.3 来源与消耗

| 类型 | 事件 | 变化（默认） | 记账对象 |
|---|---|---|---|
| 来源 | 战斗胜利 | +2~+5（按敌方势力反向） | 敌势力（降低）/己方势力（提升） |
| 来源 | 守城成功 | +4 | 该城池 + 所属势力 |
| 来源 | 赈济/解救难民 | +3 | 该城池 |
| 来源 | 交还俘虏 | +2 | 对方势力 |
| 来源 | 完成城池委托 | +2 | 该城池 |
| 来源 | 剧情抉择（`dialogueChoice`） | 直接写值 ±5~±20 | 指定势力/城池 |
| 消耗 | **主将逃亡**（§5） | **-6** | 该军团所属势力 |
| 消耗 | 就地抢掠 `army.forage`（P14 已定） | **-3** | 抢掠地所属城池/势力 |
| 消耗 | 屠城 / 烧毁民仓 | -10~-20 | 该城池 + 势力 |
| 消耗 | 任务违约/放弃 | -3 | 委托方 |
| 消耗 | 失守城池 | -8 | 该城池 + 势力 |

### 11.4 对城池的影响（全参数化，阈值表）

| 声望区间 | 态度 | 招募名额 | 交易物价 | 任务/功能 |
|---|---|---|---|---|
| ≥ 60 | 敬仰 | ×1.5 | 买 -10% / 卖 +10% | 全解锁 + 稀有兵种 |
| 20 ~ 59 | 友善 | ×1.2 | -5% | 主线全开 |
| -19 ~ 19 | 中立 | ×1.0 | ×1.0 | 基础任务 |
| -59 ~ -20 | 冷淡 | ×0.5 | +10% | 支线锁 |
| ≤ -60 | 敌视 | 禁招 | **拒售**（R3 定稿：不做 +30% 还能买，见 §11.8） | 禁止入城（需攻城） |

- 招募：`city.recruit` / `army.recruit` 的**名额与单价**乘态度系数（与模块 7 §5 `recruitCost` 相乘，不新增公式）。
- 物价：`shop.priceMultiplier` 乘态度系数（模块 2 交易）。
- **修理 / 锻造**：同样按态度系数（R3，见 §11.8 四个价格入口）；四处统一走 `PricingService.quote(kind, basePrice, {cityId})`，**只乘一次**。
- 任务：`quest.requireReputation { factionId? | cityId?, min }` 门控（任务中心条件扩展）。
- 攻城：敌视城池默认敌对（与 P10 攻城触发一致）。
- 参数全部挂 `game.project.json.reputation.attitudeTiers[]`，档位边界与系数可调。

### 11.5 与 storyState / 民心 / 士气的关系

- **存 `state.player.reputation`**（玩家个人，不存进 `storyState`；`storyState` 只放剧情事实）。
- **民心**：公式增加一项 `reputationAttitudeBonus`（±5%，按本城/本势力声望档），但**不互相替代**（民心管生产/逃散，声望管态度/交易/任务）。
- **士气**：**声望不直接改士气**（避免与逃亡惩罚重复计）；只通过招募质量间接影响（可选参数：高声望城招的兵初始士气 +5）。
- **P14 冲突检查**：`army.forage` 已定"民心 -6、声望 -3"——两本不同账（民心归城池、声望归势力），不双扣同一参数。
- **P5 冲突检查**：铜钱"取得即成数字不会被抢"与声望无关，无冲突。

### 11.6 分级实施建议与成本（定稿：做到 **R3**，R4 不做）

| 阶段 | 内容 | 成本 | 状态 |
|---|---|---|---|
| **R1 数据+展示** | `ReputationState` + 势力层 + 态度档 + HUD 一个数字（不接交易/招募） | 低（~1 人日；新增 `ReputationSystem` ~200 行 + 存档投影） | 做 |
| **R2 接模块 7** | 招募名额/价格乘系数 + `quest.requireReputation` | 中（~2 人日；2 处消费 + 1 个任务条件） | 做 |
| **R3 城池层 + 剧情写值 + 城池内价格** | `byCity` 覆写、`dialogueChoice` 写声望、敌对势力反噬、**城池内全部价格入口按态度系数**（§11.8） | 中（~3 人日：+1 人日为四处价格接入） | **做（定稿上限）** |
| **R4 个体英雄声望** | 个体英雄声望（`byHero`） | 高 | **不做**（`byHero` 字段保留为空，不实现任何逻辑） |

- **零回归保证**：不配 `reputation` 时所有态度 = 中立（系数 1.0），招募/物价/修理/锻造/任务行为与现状完全一致。

### 11.7 三参数归属：民心=城池 / 士气=两层 / 声望=玩家（2026-11-09 补充）

| 参数 | 唯一持有主体 | 存档字段 | 明确不持有该参数的实体 |
|---|---|---|---|
| **民心** | **城池**（只有城池才有居民属性） | `cityStates[cityId].morale`（模块 7） | 军团 / 关卡 / 军营 / 小队 → **一律无民心** |
| **士气·军团层** | 军团 / 城池驻军 / 关卡守军 / 军营（统一 `ArmyState`） | `armyStates[armyId].morale` | — |
| **士气·小队层** | **随行小队**（层级二 `companionSquad`） | `storyState.companionSquad.morale` | 军团主力不读它 |
| **声望** | 玩家个人 × 势力/城池 | `state.player.reputation`（§11.2） | 任何实体都不持有声望 |

**小队层士气细则**（此前只写了军团层，需单独定义）：

| 项 | 口径 |
|---|---|
| 初值 | 从来源军团抽人时 = **来源军团队士气**；新招募兵 = **60**（`squadInitialMorale`） |
| 独立变动 | 亲卫阵亡 -2/人（单场上限 -10）；连续 3 日未休整 -3/日；玩家亲自逃亡 -5（取逃亡首档，不按军团阶梯）；战斗胜利 +5；军营驻扎 +2/日 |
| 恢复 | `squadMoraleRecoverPerDay` 3；上限 100、下限 5（下限 5 防归零，`<10` 触发下行行为） |
| 下限行为 | < 10 → 随行小队自动转「防守」、拒绝「冲锋」，并提示玩家休整 |
| **不双扣** | 玩家自己就是军团主将时，`companionSquad` **就是**该军团 → 士气**只记军团层一份**，小队层仅镜像显示；只有"跟随他人 / 独立支援"时小队才有独立账 |
| 传导 | 军团层扣减**不自动传导**到独立小队层（否则一次战败扣两遍） |

> 与模块 3 的关系：03 v2.2 已去掉五军分队，所以这里的"小队"= **层级二随行小队**（`companionSquad`），不是已废的分队；`morale` 字段与上表规则**已同步**到 [模块 3](03-army-squads.md) §4.1 / §5.2 / §6。

### 11.8 R3 定稿范围：城池内价格入口（2026-11-09 第六次拍板）

**口径**：声望（按本城 `byCity` 优先、否则本势力 `byFaction`）落在**态度档**（§11.4），再换算成**一个统一系数 `attitude.priceMultiplier`**，乘以该城池内所有"对玩家报价"的价格。

| # | 价格入口 | 现有落点 | R3 是否接 | 乘算方式 |
|---|---|---|---|---|
| 1 | **商店买卖价** | 模块 2 交易 / `shop.priceMultiplier` | 接 | 买价 × 系数；卖价 × 系数（方向相反：高态度卖得更贵） |
| 2 | **装备修理费** | 修理链（`repair` 命令，模块 1/7） | 接 | 修理费 × 系数 |
| 3 | **锻造工钱** | 锻造/打造产物链（模块 7） | 接 | 工钱 × 系数（材料消耗**不乘**，只乘工钱） |
| 4 | **招募成本（含名额）** | 模块 7 §5 `recruitCost` | 接（R2 已含名额，R3 补单价） | 单价 × 系数；名额 × 名额系数（§11.4） |

**统一实现原则（防重复乘算）**：

```
城池内报价 = 基础价 × attitude.priceMultiplier(该城声望档)
  ├─ attitude.priceMultiplier 由 §11.4 态度档表派生（敬仰 0.90 / 友善 0.95 / 中立 1.00 / 冷淡 1.10 / 敌视 1.30 或拒售）
  ├─ 只在"最终报价"处乘一次（各子系统不各自乘），入口统一为 `PricingService.quote(kind, basePrice, {cityId})`
  └─ 材料/消耗品数量不乘系数（只乘货币价格），避免物价影响产出结构
```

**下限保护（不能把价格乘到 0；卖价上限只为防异常数值，不做防倒卖）**：

| 保护 | 值 | 说明 |
|---|---|---|
| 买价/修理/锻造最低 | `max(1 铜钱, 基础价 × 系数)` | 系数最低 0.90（敬仰），且价格下限 1，永不出现 0 或负数 |
| 卖价（玩家卖出所得）最高 | **`基础价 × 3`**（`sellPriceCapRatio`，第七次拍板由 `×1.10` 放宽） | **`×3` 是卖价上限，不是态度系数上限**；取消"防倒卖"理由：倒卖必须把货**实际运过去**，运输途中**可被抢**（02 押运损失表：逃 30% / 败 50% / 载具毁 100%），套利本身有风险成本，不该再用价格上限堵死；上限留在 3 倍只为防脚本/数值异常的离谱成交 |
| 系数总范围 | `clamp [0.90, 1.30]` | 与 §4 三层乘算无关（这是"报价系数"，不是战斗修正），单独 clamp；**注意：1.30 是态度系数上限，与卖价上限 3.0 是两个不同参数** |
| 敌视档 | 不减价、**拒售**（`refuseTrade: true`） | 不做"×1.30 但还能买"的极限，避免数值溢出与体验尴尬 |
| 声望负数极端 | 系数仍封在 1.30 | 不无限加价 |

- **参数**：`game.project.json.reputation.pricing { enabled, priceMultiplierByTier, minPrice, sellPriceCapRatio:3.0, refuseTradeAtHostile }`；`enabled:false` 时全部 1.0（零回归）。注意 `priceMultiplierByTier` 的取值域是 `[0.90, 1.30]`，`sellPriceCapRatio` 是另一个**卖价上限**参数（3.0），两者不可混用。
- **不做**：R4 个体英雄声望、按物品类型分别定价、声望影响掉落率。

## 12. 洗刷污点（澄清 + 定稿 hybrid）

### 12.1 原文引用（当前 06 的上下文）

1. §5 三态表「再统领该军团」行：
   > 「可以（战后），需洗刷（§12）」
2. §6 参数块：
   > `"redemption": { "mode": "hybrid", "moraleGain": 8, "reputationGain": 3 }`、`"fledWindowDays": 30`（洗刷窗口）
3. 原 v3 §10 第 5 条（现 §10-⑤）：
   > 「洗刷是否要独立任务：A 自动判定（同军团下一场胜利即回补一次） / B `army.redeem` 剧情命令」

### 12.2 「污点」到底是什么

**污点 = 逃亡留下的失格记录，不是战斗失败记录。**
具体是两条数据：

- `army.fledRecord { armyId, battleId, at, count, redeemed }`——军团层：用于连续逃亡叠加与洗刷判定。
- `commanderStigma { heroId, value, at }`——主将个人层：用于声望扣减的记账凭据（NPC 主将也记，但玩家只关心自己的）。

污点**不会**：判负、删军团、扣兵力、锁剧情；它只影响士气/声望的**回补资格**与**连续逃亡惩罚**。

### 12.3 方案与定稿（第六次拍板：选定「混合」）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 自动 | 同军团下一场胜利，自动把 `fledRecord.redeemed=true` 并回补一次士气/声望 | 零内容成本、规则可预期 | 无叙事，张角这类角色的逃亡代价显得随便 |
| B 剧情 `army.redeem` | 需专门对话/任务触发回补 | 叙事强、可按角色定制 | 每个军团都要配内容，工作量随军团数线性增长 |
| **C 混合（✅ 定稿）** | **默认 A（自动）**；**剧情主角白名单（张角等）走 B（`army.redeem` 剧情命令）** | 普通军团零成本，关键角色有代价 | 两套路径需一个白名单开关 |

**定稿：C 混合，`redemption.mode: 'hybrid'`**（此值即为默认，无需额外配置）。

```jsonc
// game.project.json → 或 battles/*.json 的 battleIntervene 块
"redemption": {
  "mode": "hybrid",                  // 'auto' | 'story' | 'hybrid'；定稿 hybrid
  "moraleGain": 8,                   // 洗刷回补士气（不超过逃亡前值）
  "reputationGain": 3,               // 洗刷回补声望
  "fledWindowDays": 30,              // 可洗刷窗口
  "storyHeroes": ["hero.zhangjiao"], // ★ 白名单（v2.3 新增字段）：这些主将的军团只能靠 army.redeem 洗刷
  "autoOnVictory": true              // hybrid/auto 下：同军团下一场胜利自动洗刷一次
}
```

| 字段 | 语义 |
|---|---|
| `redemption.mode` | `'hybrid'` = 白名单外自动、白名单内走剧情；`'auto'` = 全部自动；`'story'` = 全部走剧情 |
| `redemption.storyHeroes[]` | **白名单**（heroId 数组）：命中的主将所辖军团**不会自动洗刷**，必须由 `army.redeem` 剧情命令触发 |
| `redemption.autoOnVictory` | 自动路径的开关；`hybrid`/`auto` 下生效 |
| 白名单判定口径 | 按**该军团当前主将**（`commanderHeroId`）匹配；主将换人后按新主将重新判定 |

### 12.4 限制（防刷）

- 只在 `fledWindowDays`（30 天）内可洗刷；超期污点固化（不减上限，但不再回补）。
- 每份污点**只回补一次**（`redeemed` 置位后不可重复）。
- 回补不超过逃亡前值（士气/声望）。
- 洗刷只解除**一次**连续逃亡叠加计数（`count -= 1`，不归零）。

## 16. 最小可玩形态（S12 试点 + S02 远程接管/支援）

1. 触发器下发 `unit.order { order:'attack', target: S12 }`（或敌军来攻）→ PREVIEW。
2. 玩家不在 S12 → PREVIEW → 战果卡 → 资源/伤亡入档 → 任务推进。
3. 玩家走进 S12（现场接管）→ 展开 LIVE；越过边界弹确认，确认=逃亡。
4. 另一支友军军团在 S12 交战时，玩家抵达同场景按「支援」→ 独立小队参战，无指挥权、离开无惩罚。
5. S02：`armyCampLaid` 后剧情发 `army.possess`（= `joinBattle{takeover,remote}`）→ 操作张角 → 退出即逃亡（回最近军营〔战场即该营则退最近的他营/城镇，§5.6〕、士气/声望扣、本场不可再接管）→ 部队由预演打完。
6. 验收：①展开/收回不重复结算；②三态不改胜负出口；③逃亡参数可配且重于战术撤军；④支援不改军团阵型/姿态、不判负、每场限一次；⑤未确认无法离开战场；⑥不配新数据零变化；⑦**战中改部署（兵种/阵型/主将位置）任何身份都被拒**；⑧旁观/支援时主将 AI 接管且光环生效。
