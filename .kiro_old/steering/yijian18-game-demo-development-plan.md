# 《三国张角传》可交付开发计划

本计划把 `#[[file:../specs/yijian18-game-demo/requirements.md]]` 转换为可执行交付顺序。需求与验收条件仍是范围事实来源，`#[[file:../specs/yijian18-game-demo/design.md]]` 是架构依据，`#[[file:progression-implementation.md]]` 是已完成基础设施事实来源；冲突时按“需求 > 用户已确认决策（本计划第 2 节）> 设计建议 > 实现现状”处理。

**玩家流程与文案入口**：玩家从新游戏、S01–S14、南阳／西华互斥路线到六结局的完整游玩顺序、对白、提示及文案修改位置，统一维护在 `#[[file:../../docs/PLAYTHROUGH_SCRIPT.md]]`。本计划负责范围裁决、阶段安排、系统约束和完成门槛；`PLAYTHROUGH_SCRIPT.md` 负责玩家实际经历的先后顺序与可编辑文案。实施场景时必须同时核对两者，流程文案不得绕过本计划第 2 节的已锁定决策，代码完成状态也必须按剧本中的 `【已实现】／【待补】` 如实标记。

## 1. 最终目标

直接升级现有 `example/sanguo_zhangjiao/`，交付名为 **《三国张角传》** 的单机 Demo：玩家能够从 S01 新游戏连续玩到 S14，可以保存和恢复、选择路线并得到六种结局之一。它不是系统功能陈列或测试关卡，必须具备完整开场、教学、探索、战斗、采集、剧情、场景转换、成长、战争反馈、结局演出和可发布资产。

原 requirements 的“正式美术资产生产不在范围内”仅排除商业完整版规模，不再表示允许资源缺失。本计划新增 **Demo 成品美术与音频 Pass**：缺少正式图片时允许使用图标或 AI 生成图片作为已登记的临时资产，后续可在编辑器中按稳定图片 ID 或直接替换图片文件。发布包不得含未登记占位图、调试几何体、断链资源、版权不明素材或只为验证功能存在的临时 UI。

发布主表现以 Canvas 2D 为准。three.js 3D 前期直接使用 2D 图片生成 billboard/sprite，位置复用 2D 编辑器坐标：2D `x` 映射 three.js `x`，2D `y` 映射 three.js `z`，`elevation` 映射 three.js `y`。3D 与 2D 必须共享任务条件、战果和 StoryState；后期可按相同 assetId 替换为低模或正式 3D 资源，不要求两种后端达到相同美术精度。

## 2. 已锁定的实施决策

以下均为用户已确认决策，优先于 design.md 中的推荐选项，除非用户再次明确更改：

- **现有游戏升级**：直接升级 `example/sanguo_zhangjiao/`，名称固定为《三国张角传》，不创建第二个游戏 Demo。
- **旧剧情处理（1C）**：删除旧六幕剧情事实，不保留 legacy campaign；只复用框架能力和授权清晰、仍适用的美术资源。旧 `final_rescue`、旧 ending、旧 act 变量和旧对白不得进入新 StoryState。
- **场景 ID（2C）**：运行时 canonical ID 直接改为 `S01`–`S14`，不提供 `s0-0` 等旧 ID alias；触发器、传送、`_scene_order.json`、StoryState 和新存档只写 SXX。
- **场景与 chunk（3C）**：普通场景一个主 chunk，chunk ID 与 SXX 相同；大型战场允许多个 chunk，SXX 是业务场景和入口主 chunk，附属 chunk 使用 `SXX-CNN` 命名并在同一 SceneDynamicState 命名空间下保存。
- **旧存档（4C）**：旧 schema、旧 chunk、旧 act 和旧职业存档全部不兼容，不提供迁移；新版本必须拒绝加载并提示开始新游戏。物理删除仓库存档文件或用户本地数据属于后续实施动作，本计划不自动执行。
- **职业（5C）**：删除 `mage`，第三职业 canonical ID 只使用 `strategist`，显示名“军师”，不提供旧职业兼容。
- **流式加载（6A）**：`src/core/WorldStreamingManager.js` 为唯一管理器；`WorldMapLoadSession`、`ChunkNavigator`、`PlacementSpawner` 作为现有加载/传送适配器接入，`src/systems/WorldStreamingManager.js` 完成调用方迁移后淘汰，禁止机械替换 API。
- **Android（7A）**：根 `capacitor.config.json` 和根 `android/` 是唯一发布权威，目标为 `appId: com.sanguo.zhangjiao`、`appName: 三国张角传`、`webDir: dist/sanguo_zhangjiao`；Demo 内 mobile 工程仅作 legacy，禁止长期双写。
- **美术与资源（8A，最新决定）**：现有及后续使用的图片、音频、模型和其他资源均按“项目原创或已获授权”处理，当前开发不执行逐项授权、版权、作者或来源核验，也不把这些字段作为阶段或发布阻断项；本计划其他章节中关于授权/版权/来源审计的旧文字均由本条覆盖。所有 2D 图片的运行时与可替换文件统一使用 PNG：现有 SVG 与 WebP 必须完整迁移为同效果 PNG，普通静态背景也不得保留 SVG 或 WebP；后续新增图片一律使用 PNG，禁止创建 SVG 或 WebP 图片文件。PSD 仅允许作为仓库外或独立美术源目录的制作文件，禁止放入运行时资源路径、作为 Manifest 的 `sourceFile`／`runtime2D`／`runtime3D`，或由 AssetManager 加载。资源工作只检查稳定 `imageId/assetId`、文件与引用完整性、替换能力、状态、尺寸、pivot、动画及 2D/3D 映射。缺图时**默认自动生成 PNG**并登记接入，不询问、不保留代码色块或兜底圆点，具体流程见第 15.1 节。除图片切割后生成的 slice 对象外，所有图片必须具有稳定 `imageId/assetId`，并在编辑器提供“更换资源 ID”和“替换图片文件且保留 ID”两种方式；slice 使用稳定源图片/图集 ID 加裁剪区域、索引或 `sliceKey`，不强制独立 ID。
- **3D（9A）**：2D 是正式发布主表现；3D 前期使用相同 2D 图片的 billboard/sprite，并直接复用 2D 编辑器位置、尺寸、pivot 和 elevation，业务状态完全一致；后续替换 3D 模型不得改变业务 ID 或场景坐标。
- **测试（10B）**：允许在每个 P 阶段出口运行相关的针对性 Vitest 和必要 diagnostics；不自动运行全量测试或生产构建，除非用户另行要求。
- **成长系统**：传统职业树 + 暗黑式分支 + 30–60 节点小型 Passive Board；复用 ProgressionGraphSystem、EffectResolver 和旧 API 适配层。
- **分层边界**：Schema、事务、状态机、成长图、Checkpoint、契约进入引擎；历史人物、S01–S14 场景、对白和结局留在《三国张角传》。
- **战斗服务**：当前只实现同契约 LocalMockTransport，外部 transport 留接口。

## 2.1 与原始策划案的差异裁决

事实源顺序为「本计划 > `元宝设计补充1.txt` > `元宝设计.txt`」。以下差异已裁决，实施时不再回退到旧策划文字：

| 项目 | 策划案 | 本项目裁决 |
|---|---|---|
| 作品名 | 《一剑十八年》 | 《三国张角传》，`yijian18-engine` 只是引擎名 |
| 仓库结构 | engine + server(Go) + slg(Go) 三仓 | Demo 为单机，只保留 `BattleClient` 契约与 LocalMockTransport；不建 server/slg 仓库 |
| 语言与 Schema | TypeScript + `src/schema/` + protobuf | ES6 JS + `src/data/schema/`，无 TS 生成与 proto；字段语义保持一致以便后续接外部服务 |
| 第三职业 | `mage` | `strategist`／军师，无旧职业兼容 |
| 结局数量 | 主案 5 结局 | 6 结局，补充案的隐藏「焦土」升为正式结局，并固定优先级：焦土 → 旁观者 → 火种 → 余烬 → 流星 → 尘埃 |
| 地图事实源 | 20×20 ASCII 网格与 `(row,col)` | 用户确认的 20×20 `(row,col)` 是世界布局事实；唯一实际配置保存在 `game.project.json -> worldMap.regions[].grid`。各 Region 使用同一全局 20×20 坐标，场景 JSON 只保存 chunk 局部坐标，`worldOffset = (col×1280,row×720)` 由运行时派生且只应用一次；未完成场景用 `reserved:true` 单元保留规划位置但禁止加载 |
| 建造耗时 | 补充案 4.1 说资源够即「瞬间完成」，二.1 说「不能瞬间完成，除非 damage>0.5」 | 采用后者：普通施工必须走工期，仅城损 >0.5 的抢修缩短工期并以 50% 初始耐久完成 |
| 捐粮士气 | 补充案写「士气 +5%」 | 实现为绝对值 `morale + 5`，CityState 士气为 0–100 整数，不使用百分比叠加 |
| 采集工具耐久 | 示例「铁斧 30」 | S01 开局为「破旧斧头」耐久 8，体现开局窘迫；后续工具可按 30 量级配置 |

补充案中以下设计点必须落地，之前未在阶段条目中写明：

1. **工具损毁的处境后果**（补充案 一.2）：斧断=被困林中无法继续伐木撤离、镐断=矿坑内无法开路撤退、铲断=在建临时工事作废。每类损毁必须给出明确处境反馈与可行退路，不能只弹「工具损坏」。
2. **S05–S06 第一次失去工具**（补充案 五）：在南阳线安排一次「工具在战斗中损毁、被迫徒手撤退」的强制体验，作为工具压力的叙事高点。
3. **强硬分支的后续代价**（补充案 四.3.A）：强硬路线除士气提升外，必须写入「严苛统领」标签，并在当日夜晚有概率触发逃亡事件；标签与事件都进 StoryState，且只结算一次。
4. **采集与营建作为结局隐藏输入**（补充案 五、结局联动）：全程采集与城市维护水平、是否只采集不参战、是否放任城市损毁，必须作为 EndingSystem 的显式输入字段参与优先级判定，而不是只看四武将生死。
5. **最终战的资源收束**（补充案 五）：终局必须出现「带最后的马车突围」与「投石车因缺木料无法组装」两种由资源状态决定的实际分歧。
6. **昏迷后扎营与沿溪筑城**（补充案 22、23）：特殊昏迷后的被救、临时扎营、「离水源远、只能住几天、不惧小股官兵、不适合筑城」的说明、拔营，以及顺溪而下寻找筑城地并筑城，属于 P4 必做内容而非可选风味。

## 3. 执行纪律

1. 每阶段先完成一条可从玩家入口实际游玩的纵向切片，再批量扩内容；禁止先堆完框架再补游戏。
2. 通用能力优先复用现有 ECS、InputHints、Pickup、Inventory、Vehicle、Trigger、Snapshot、Scene Runtime、双渲染适配器；禁止在 Demo 重建第二套同类系统。
3. 所有状态修改遵循 `validate → prepare draft → commit → emit → checkpoint`；失败零修改，重复 operationId 幂等。
4. 每个场景同时完成玩法、剧情、UI、音画、存档和重载，不把美术接入统一拖到 P6。
5. 磁盘 JSON 是场景唯一真实源；编辑器保存必须同时写 JSON 与 localStorage，缓存缺少 `layers` 时从文件恢复。
6. 操作提示必须走 InputHints，并覆盖 pc/android/gamepad；图片和对白中不得烘焙固定按键。
7. 场景对象始终从只读局部坐标投影；每个 LogicalObject 只应用一次 worldOffset，碰撞和表现派生自同一世界坐标。
8. 场景、角色、UI、图标和 3D fallback 禁止硬编码不可替换图片路径；统一引用稳定 imageId/assetId，编辑器保存 ID 和可替换文件映射。图片切割后的 slice 对象除外：slice 可保存源图片/图集 ID 与裁剪区域、索引或切片名，不要求每个 slice 单独注册 imageId/assetId，但源图片/图集必须可替换。
9. 3D billboard 使用 Transform3DAdapter 的统一映射，不在 3D 后端维护第二套位置；2D 编辑器修改坐标后两种后端同时生效。
10. 不创建功能验证 HTML 页面；日常修改只运行 diagnostics，每个阶段出口允许运行针对性 Vitest，完整构建仍由用户决定。

## 4. 目标目录与所有权

开发直接在现有《三国张角传》目录中升级；复用入口、框架接线、编辑器能力和可用美术，但旧剧情、旧场景 ID、旧职业与旧存档格式不作为兼容目标。实施时只增加当前阶段实际需要的内容：

```text
example/sanguo_zhangjiao/
├── index.html                    # Demo 唯一入口
├── game.project.json             # 系统、注册表、起始场景与 LocalMock 配置
├── config/                       # 数值、输入提示、成长图、战役/救援/结局定义
├── assets/
│   ├── manifests/                # 稳定 assetId、授权、2D/3D 映射和预算
│   ├── scenes/                   # S01-S14 与 _scene_order.json
│   ├── images/ atlases/ audio/   # 运行时成品资产
│   └── models/                   # 3D fallback/低模资产
├── data/                         # Story、City、War、ResourceNode 初始定义
├── entities/                     # Demo 实体模板和角色装配
├── scenes/                       # 薄场景组合根，不堆历史规则
├── systems/                      # 仅 Demo 历史编排适配器
└── saves/                        # 开发环境快照镜像，不提交玩家存档
```

引擎新增能力放入现有职责目录：Schema 在 `src/data/schema/`，校验复用 `src/core/validation/`，领域系统放 `src/systems/`，战斗契约放 `src/integration/`，UI ViewModel/Panel 放 `src/ui/`。历史人物、固定月份、场景坐标、对白、救援目标和结局演出不得进入 `src/`。

## 5. “完成”的统一定义

### 5.1 单项功能完成

- 有玩家可到达的入口、成功反馈、失败反馈和退出路径。
- 正常、边界、失败回滚、重复提交、保存恢复五类行为均成立。
- 数值来自配置；业务状态不保存在渲染对象或 UI 控件中。
- PC、Android、gamepad 的提示由 InputHints 生成。
- 2D 可完整操作；3D 使用同一命令和业务状态。
- 资源、监听器、计时器和异步任务在场景退出时释放。

### 5.2 单个场景完成

- 场景有唯一视觉主题、入口、出口、主目标、至少一个可选探索反馈和明确完成反馈。
- 地形、阻挡、walkable、出生点、交互点、战斗区、镜头和小地图可用。
- 剧情对象、敌人、节点、掉落、工事和载具的动态状态可卸载后恢复。
- 对话、任务、UI、VFX、SFX、环境音和音乐切换均已接入，不接受“以后统一补”。
- 从前一场景自然进入并能进入下一场景；失败后可继续、重试或读档。
- 无未批准占位、断链资源、硬编码平台按键和 worldOffset 漂移。

### 5.3 阶段完成

- 阶段主流程可从正常入口游玩，不依赖控制台改状态。
- 阶段门槛对应的需求验收项有实际运行证据或自动化证据。
- 新增 Blocker/Critical 缺陷为 0；未完成项不得以“已有类名”冒充完成。
- 阶段存档能加载到下一阶段，Schema 版本和迁移策略明确。

## 13. P6：全图、性能、Polish 与发布候选（2 周）

### P6.1 世界流式与恢复

1. `src/core/WorldStreamingManager.js` 统一管理 Region 内九宫格：进入网格加载当前与相邻八格，曼哈顿距离>2 卸载；`WorldMapLoadSession`、`ChunkNavigator`、`PlacementSpawner` 作为数据加载、传送和实例化适配器。
2. 普通 SXX 主 chunk 与大战场 `SXX-CNN` 附属 chunk 使用同一业务场景命名空间；卸载前保存各 chunk 动态状态，返回后完整恢复。
3. RegionCoordinator 两阶段切换：保存旧区草稿→加载/校验目标→shadow restore→一次提交 Region/位置/Story→释放旧区。
4. 目标加载失败时旧 Region、位置和 Story 不变，错误显示目标 Region/Scene 和原因，玩家仍可操作。
5. 连续往返所有边界，检查资源、敌人、建筑、载具、掉落、剧情对象和坐标；禁止重复偏移与共享引用。
6. 所有调用方迁移完成后淘汰 `src/systems/WorldStreamingManager.js`；在此之前仅允许兼容转发，不允许两套管理器同时拥有运行状态。

### P6.2 性能和稳定性

1. 锁定并记录 Reference Profile、浏览器/设备、分辨率、渲染模式、采样时长、版本和场景存档。
2. S11 至少 100 活动 ECS 实体持续指定时长，平均帧率≥60；同时观察 1% low、长任务和 draw call，避免平均值掩盖卡顿。
3. 同 Region 连续跨边界后运行内存<100MB；检查实体、timer、listener、粒子、Canvas 代理、非共享纹理和异步回调释放。
4. 对同一新版本存档、seed 和命令序列比较 2D/3D 的任务、BattleResult、Story/City/War 状态，业务 diff 必须为零；3D billboard 的 x/z/elevation 与 2D 编辑器数据一致。
5. 检查点执行两轮 save/load 等价；损坏、高版本或缺字段的新存档不覆盖原存档且运行状态不变，旧版本存档按已确认政策直接拒绝，不进入迁移。
6. 键鼠、目标 Android 触屏和 Xbox 360 手柄分别完成新游戏、教学、战斗、面板、载具、存读档和结局冒烟。
7. 阶段出口运行受影响模块的针对性 Vitest 和 diagnostics；不自动扩大为全量测试或生产构建。

### P6.3 全量美术与发布整理

1. 扫描 Manifest：未登记 placeholder、缺文件、重复 ID、无来源、错误 pivot/bounds、缺动画状态和未映射 3D fallback 必须清零。非 slice 图片必须有稳定 ID；slice 对象只需保证源图片/图集 ID 和裁剪数据有效。图标或 AI 临时图可以保留为已批准临时资产，但必须有来源/status 和人工替换入口。
2. 合并 atlas、复用纹理和材质、压缩图片/模型/音频、按 Region 分组懒加载；优化或替换图片不得改变稳定 assetId/imageId。
3. 完成遮挡、Y-sort、碰撞边界、小地图、移动端字号/触控区、色彩对比、VFX 强度和音量混音的统一 Polish。
4. 完成 Logo、封面、真实运行截图、版本号、第三方授权/署名数据和发布包图标；宣传图必须来自实际版本。
5. 使用根 Capacitor 配置和根 Android 工程，从干净环境检查安装/启动/新游戏/新版本读档/通关/返回标题；旧存档只验证会被明确拒绝，不作为回滚兼容目标。

### P6.4 Release Candidate 门槛

- R23 的 2D 完整渲染、3D 状态一致、100 实体 60 FPS、内存<100MB、旧区释放全部通过。
- S01–S14 主流程、两条豫州路线、观战/介入、四武将生死、三职业、六结局均至少完成一次组合覆盖。
- Blocker/Critical 为 0；High 仅允许有明确影响、规避方式和批准期限的例外。
- 无未登记占位、断链、版权不明资源、调试几何体或只用于验证的临时 UI；已批准图标/AI 临时图必须可按原 ID 替换，且不阻断业务流程。
- 根 Android 工程可构建目标包，Demo mobile 配置不参与发布。
- 发布构建、配置和资源 revision 固定，形成可对外提供的 Release Candidate，而不只是“可玩候选”。

## 15. 美术生产与引擎接入流程

1. **Brief**：明确 assetId、场景用途、镜头距离、状态、动作、尺寸、pivot、bounds、阵营色、目标阶段和复用范围。
2. **灰盒**：用批准的灰盒验证动线、碰撞、交互距离和镜头，不在灰盒上烘焙业务状态。
3. **概念/样板**：先完成 S01、S09、S11 样板；通过轮廓、色彩、信息层级和生产成本评审后再批量复制规则。
4. **制作与临时替代**：角色/载具按统一动作语义，环境按模块化套件，UI 图标遵循同一网格和描边。PSD 仅可作为仓库外或独立美术源目录的制作文件，不得进入运行时资源目录、Manifest 或 AssetManager；所有接入项目的图片必须导出为 PNG。正式图片缺失时可使用通用图标或 AI 生成图，但必须立即分配稳定 imageId/assetId 并标记状态。
5. **导出**：2D 图片统一使用 PNG；如需图集，图集页面同样必须为 PNG。3D 初期直接从 runtime2D 创建 billboard/sprite，后期正式模型使用 glTF/共享材质；音频使用项目统一格式。禁止把编辑源文件当运行资源。
6. **编辑器替换**：所有非 slice 图片字段显示当前 imageId、预览和来源，并同时支持“选择其他 ID”和“替换当前 ID 对应文件”。替换文件必须保留场景引用；修改 ID 必须同步磁盘 JSON、全局图片配置、内存缓存和所有场景 localStorage 缓存。图片切割后的 slice 对象显示源图片/图集 ID、裁剪区域和切片索引/名称，通过替换源资源统一更新，不强制分配独立 ID。
7. **自动检查**：检查非 slice 图片的缺文件、重复 assetId/imageId，以及 slice 的源资源、裁剪区域和索引/名称有效性；同时检查尺寸、透明边、pivot、bounds、动画名、材质、文件大小、授权/生成来源和 placeholder 状态。
8. **接入**：AssetManager/Registry 对非 slice 图片引用 assetId/imageId；slice 对象通过稳定源图片/图集 ID 加裁剪数据解析。2D/3D adapter 负责映射；表现资源不得成为 Story/战果/存档事实源。
9. **场景装配**：编辑器写磁盘 JSON 并同步缓存；碰撞与 walkable 独立于图片/模型私有几何，walkable 优先于 collide。
10. **3D fallback**：EntityView3D 优先使用同 assetId 的 2D 图片创建 billboard/sprite；Transform3DAdapter 统一执行 `2D x → three.x`、`2D y/z → three.z`、`elevation → three.y`。禁止在 3D 配置中复制一套位置。
11. **双后端检查**：同一实体共享图片/模型语义状态、尺寸、pivot、动画状态和业务 ID；缺 3D 专属资产时使用 runtime2D fallback，不允许静默消失。
12. **验收与冻结**：场景负责人、程序和美术共同检查遮挡、层级、交互、动画、音量、移动端可读性、反复加载和资源释放；通过后锁 revision。

## 15.1 缺图自动生成（默认行为，无需询问）

发现任何内容缺少图片时，默认立即生成并接入，不停下询问、不保留代码色块或兜底圆点、不以“美术待补”为由跳过：

1. **先复用**：查 `assets/manifests/assets.json` 和 `assets/images/`，已有可用资源直接引用其稳定 ID，禁止为同一内容重复建 ID 或重复生成图片。
2. **生成格式**：统一生成 PNG 并放入 `assets/images/<场景或分类>/`，文件名用 kebab-case。现有 SVG 与 WebP 必须完整替换为同效果 PNG，普通静态背景也在迁移范围内；后续新增图片一律使用 PNG，禁止创建 SVG 或 WebP 图片文件。PNG 必须按目标展示尺寸或更高的合理分辨率导出，不得放大低分辨率图冒充高清。
3. **规格**：世界物件（资源节点、道具、建筑、角色）pivot 为脚底中心 `{x:0.5,y:1}`，UI 图标为居中 `{x:0.5,y:0.5}`；尺寸与同类已有资源对齐（资源节点约 64×56，角色 54–82 高，掉落道具 32–48）；配色取 `config/presentation.json` 的 `palette`，保持低饱和土黄灰褐主调与阵营色区分。
4. **登记**：在 Manifest 追加条目，`assetId` 与 `imageId` 同值，命名 `<场景或域>.<类别>.<名称>`（如 `s01.resource.dryWoodNode`）；填写 `category/usage/sourceFile/runtime2D/runtime3D/pivot/bounds/animations/targetPhase/revision`，生成图 `status` 记 `ai-generated`，复用第三方图记 `third-party-approved`。
5. **接线**：把稳定 `imageId` 和 sprite 尺寸写进内容定义（`library.items`、`resourceNodes`、`enemies`、`npcs` 等）；场景 JSON 只引用 ID。禁止在场景、实体或 UI 中硬编码图片路径。
6. **框架缺口自己补**：某类对象的渲染路径还不消费稳定 ID（历史上地面拾取物只有硬编码手绘表）时，先把“稳定 imageId 优先 → 已有手绘/代码样式 → 通用兜底”的解析补进框架渲染器，并让放置点预载图片，再接内容；不要在 Demo 里另写一套图片解析。
7. **替换友好**：生成图是临时资产，不阻断流程；后续换正式美术必须保留原 ID 与场景引用，只替换文件或 Manifest 路径。
8. **边界**：生成的图片只是表现层，不得成为任务、战果、库存或存档的事实源；不得用生成图替代已明确要求的正式演出内容而跳过验收。

## 16. 内容生产顺序

每个场景严格按以下顺序交付，避免“地图画完但不能玩”或“逻辑完成但无法发布”：

1. 场景一句话体验目标和前后置 StoryState。
2. 灰盒地形、阻挡、出生/出口、镜头和关键交互点。
3. 主目标状态机、失败/恢复路径和 checkpoint 时点。
4. 敌人、资源、工事、载具、NPC 和掉落配置。

6. UI 提示和三输入方案操作文案。

8. 2D/3D 业务一致、卸载恢复、worldOffset 和资源释放检查。
9. 从前一场景进入并到下一场景的实际通玩。
10. 将场景状态从 `greybox` → `playable` → `contentComplete` → `releaseReady`，不得跳级。

## 17. 验收证据与缺陷策略

### 17.1 证据类型

- `unit`：Schema、事务、状态机、优先级、边界和幂等的 Vitest。
- `scenario`：使用实际系统和配置执行场景命令序列，不创建独立测试 HTML。
- `saveFixture`：用于职业、路线、四武将和六结局组合的版本化合法存档。
- `playthrough`：从玩家入口录制/记录实际步骤、版本、输入方案和结果。
- `profile`：帧率、内存、实体数、场景、设备和采样时长记录。
- `assetAudit`：Manifest、授权/生成来源、placeholder、断链、可替换 ID、大小和 2D/3D 映射结果。

自动执行权限固定为：平时编辑后运行 diagnostics；每个 P 阶段出口可运行与该阶段相关的针对性 Vitest。全量测试、覆盖率和生产构建仍需用户另行要求。

### 17.2 缺陷优先级

- Blocker：不能启动、不能继续主线、存档损坏/覆盖、状态永久错误、发布包缺关键资源；立即阻断阶段。
- Critical：资源复制/丢失、结局/路线错误、跨区回滚失败、主要平台频繁崩溃；阶段出口前必须清零。
- High：主要玩法、输入方案、音画反馈或性能明显不达标；RC 原则上清零。
- Medium/Low：不阻断完成且有稳定规避路径；记录影响场景和目标阶段。

既有测试失败只可作为冻结白名单，新增失败不得加入白名单逃避修复。修改白名单涉及模块时，应判断是否仍与当前改动无关。

## 19. 实施优先级与防偏航规则

当时间不足时按以下顺序取舍：

1. 不可削减：S01–S14 可通、存档安全、状态原子/幂等、三职业、两路线、四救援、六结局、2D 完整表现、发布资产合法。
2. 可缩减但不能删除：成长图节点数量、非关键敌人变体、支线对白长度、VFX 层数、3D 美术精度。
3. 可延后：商业级配音、完整大型 POE 盘、外部服务 Transport、长期 SLG、多人、跨设备存档。
4. 禁止以降级名义删除需求明确要求的目标行为；R1.5 的降级只在兼容增量确实不可行时使用，并且主线仍须可完成且玩家获得明确反馈。
5. 禁止为了“完成系统”长期不制作场景；连续两个工作批次没有新增可玩分钟数时，下一批次必须优先纵向切片。
6. 禁止把 P6 当作内容垃圾桶；P5 结束时场景、剧情、主要资产必须 Content Complete。

## 20. 计划维护方式

- 本文件记录稳定开发顺序、门槛和约定，不写每日进度或一次性调试日志。
- 实施状态应标记为 `notStarted / inProgress / blocked / done`，只有满足对应出口门槛才可标 done。
- 新发现的通用根因和长期约定更新到对应已有 steering；一次性缺陷留在任务/问题系统。
- requirements 发生范围变化时，先更新 Spec，再同步本计划的阶段、资产和门槛；不得只改计划绕过验收条件。
- 每完成一个小任务继续执行同阶段下一项；仅在高风险破坏性操作、需求冲突或缺少不可推断的产品输入时停下询问。
